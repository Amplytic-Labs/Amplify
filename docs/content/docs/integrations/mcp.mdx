## What is MCP?

The **Model Context Protocol (MCP)** is an open standard that enables AI models to interact with external tools and data sources through a unified interface. Amplify uses the `@modelcontextprotocol/sdk` (v1.29.0) to connect to MCP-compatible servers, allowing the AI to call tools from any MCP server alongside Amplify's built-in tools.

MCP turns Amplify into a pluggable platform: instead of hard-coding every capability, the AI can dynamically discover and invoke tools from third-party servers — file systems, databases, APIs, browser automation, and more.

## Transport Types

Amplify supports three MCP transport types, each suited to different deployment scenarios:

### Stdio

Spawns a local process and communicates over stdin/stdout. Ideal for local CLI tools and server-side integrations.

```json
{
  "mcpServers": {
    "my-local-tool": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@my-org/mcp-server"],
      "env": { "API_KEY": "..." }
    }
  }
}
```

**Configuration fields:**

| Field     | Type                 | Required | Description                                  |
|-----------|----------------------|----------|----------------------------------------------|
| `type`    | `"stdio"`            | Yes      | Transport type identifier                    |
| `command` | `string`             | Yes      | The command to spawn (e.g. `npx`, `node`)   |
| `args`    | `string[]`           | No       | Arguments passed to the command              |
| `cwd`     | `string`             | No       | Working directory for the spawned process    |
| `env`     | `Record<string>`     | No       | Environment variables for the child process  |

### SSE (Server-Sent Events)

Connects to a remote MCP server over HTTP using server-sent events for streaming responses. Works with servers that expose an SSE endpoint.

```json
{
  "mcpServers": {
    "my-remote-tool": {
      "type": "sse",
      "url": "https://my-server.example.com/sse",
      "headers": { "Authorization": "Bearer ..." }
    }
  }
}
```

**Configuration fields:**

| Field     | Type                 | Required | Description                                  |
|-----------|----------------------|----------|----------------------------------------------|
| `type`    | `"sse"`              | Yes      | Transport type identifier                    |
| `url`     | `string` (URL)       | Yes      | The SSE endpoint URL                         |
| `headers` | `Record<string>`     | No       | Custom HTTP headers (e.g. auth tokens)       |

### StreamableHTTP

An HTTP-based transport that supports request/response and optional streaming. This is the newest MCP transport type, designed for modern HTTP deployments.

```json
{
  "mcpServers": {
    "my-http-tool": {
      "type": "streamable-http",
      "url": "https://my-server.example.com/mcp",
      "headers": { "Authorization": "Bearer ..." }
    }
  }
}
```

**Configuration fields:**

| Field     | Type                 | Required | Description                                  |
|-----------|----------------------|----------|----------------------------------------------|
| `type`    | `"streamable-http"`  | Yes      | Transport type identifier                    |
| `url`     | `string` (URL)       | Yes      | The MCP endpoint URL                         |
| `headers` | `Record<string>`     | No       | Custom HTTP headers (e.g. auth tokens)       |

## MCPService Architecture

The `MCPService` is a **singleton** class that manages all MCP connections and tool registration. It follows a strict initialization pattern:

```ts
const mcpService = MCPService.getInstance();
```

### Configuration Validation

All server configurations are validated through **Zod schemas** before use. This ensures type safety and catches misconfigurations early:

- `stdioServerConfigSchema` — validates stdio transport configs
- `sseServerConfigSchema` — validates SSE transport configs
- `streamableHTTPServerConfigSchema` — validates StreamableHTTP transport configs
- `mcpServerConfigSchema` — union of all three schemas
- `mcpConfigSchema` — validates the full `{ mcpServers: Record<string, MCPServerConfig> }` structure

Invalid configurations produce descriptive error messages with field-level detail, helping users fix problems quickly.

### Tool Conversion

When an MCP server connects, its tool definitions are converted from MCP format to **AI SDK Tool format**. This bridge layer handles:

1. **Schema mapping** — MCP's JSON Schema parameters → Zod schemas compatible with the AI SDK
2. **Tool registration** — Each MCP tool is added to the unified tool registry alongside built-in tools
3. **Execution routing** — When the AI calls a tool, the service routes it to the correct MCP client
4. **Server tracking** — A `_toolNamesToServerNames` map ensures each tool invocation reaches the right server

### Internal Tools

Amplify registers approximately **15 built-in tools** alongside any MCP tools. These are organized into four categories:

| Category         | Tools                                                                                                                                 | Count |
|------------------|---------------------------------------------------------------------------------------------------------------------------------------|-------|
| **Native**       | `read_file`, `list_dir`, `find_files`, `grep_search`, `replace_string_in_file`, `multi_replace_string_in_file`, `create_file`, `web_search` | 8     |
| **Memory**       | `update_user_memory`, `read_user_memory`                                                                                             | 2     |
| **Vector Store** | `search_user_context`, `store_user_fact`, `search_project_context`, `store_project_context`                                          | 4     |
| **Planning**     | `execute_plan`                                                                                                                        | 1     |

**Native tools** mirror VSCode Copilot's design: read-only tools (`read_file`, `list_dir`, `find_files`, `grep_search`) operate on the file snapshot shipped with each chat request, while mutating tools (`replace_string_in_file`, `multi_replace_string_in_file`, `create_file`) return structured mutation signals that the browser-side workbench applies.

**Memory tools** use `MemoryStore` for simple string-based recall — lighter than the vector store but useful for quick facts.

**Vector store tools** provide BM25-ranked semantic search over user profile and project context, with browser-only execution (guarded by `typeof window` checks).

**Planning tools** enable multi-step task decomposition with user approval before execution.

## MCP Store (Zustand)

The `useMCPStore` is a Zustand-managed state store that handles MCP configuration on the client side. It provides:

- **Settings persistence** — Config is saved to `localStorage` under the key `mcp_settings`
- **Initialization** — On first load, the store reads saved config and connects to configured servers
- **Config updates** — The `updateSettings` action sends config to the server and updates available tools
- **Server availability checks** — Periodic `checkServersAvailabilities` calls verify servers are reachable

### Default Settings

```ts
const defaultSettings = {
  maxLLMSteps: 5,
  mcpConfig: {
    mcpServers: {},
  },
};
```

The `maxLLMSteps` setting (default: **5**) controls how many tool-call iterations the AI can perform in a single chat turn. This prevents runaway tool chains.

## API Routes

Two API routes manage MCP server lifecycle:

### `/api/mcp-update-config`

Accepts a `POST` request with an `MCPConfig` body. The route:

1. Validates the config structure
2. Calls `MCPService.getInstance().updateConfig(config)`
3. Returns the updated `MCPServerTools` map with availability status for each server

### `/api/mcp-check`

A `GET` endpoint that checks all configured MCP servers for availability. Returns a `MCPServerTools` map where each server entry has either:

- `status: "available"` — with the discovered tools and a connected client
- `status: "unavailable"` — with an error message describing why the server couldn't connect

## Settings UI

The MCP configuration interface is accessible through the **Settings** panel in the sidebar. It provides:

- A list of configured MCP servers with status indicators
- Add/edit/remove server forms for each transport type
- Auto-detection of transport type based on input fields (a `command` field → stdio; a `url` field → SSE or streamable-http)
- Real-time availability checking after config changes

### Adding MCP Servers via UI

1. Open **Settings** → **MCP Servers**
2. Click **Add Server**
3. Fill in the server configuration:
   - For **Stdio**: enter the `command`, optional `args`, `cwd`, and `env`
   - For **SSE**: enter the `url` and optional `headers`
   - For **StreamableHTTP**: enter the `url` and optional `headers`
4. The system validates the config and attempts to connect
5. Available tools from the server appear in the tool registry

## Tool Approval/Denial Flow

Amplify implements a **human-in-the-middle** approval flow for tool executions:

1. The AI generates a tool call during the streaming response
2. The tool call is annotated with `TOOL_EXECUTION_APPROVAL` or `TOOL_EXECUTION_DENIED`
3. Built-in tools with `execute` functions run automatically on the server
4. MCP tools require the server to be connected and available
5. If a tool has no execute function (`TOOL_NO_EXECUTE_FUNCTION`), it returns a description-only result
6. Errors during execution produce `TOOL_EXECUTION_ERROR` annotations

This flow ensures that:

- **Safe read-only tools** execute without user intervention
- **Mutation tools** can be reviewed before their effects are applied (via the workbench store)
- **MCP tools** from untrusted servers can be audited through the availability check system
- **Client-side tools** (vector store, memory) only execute in browser context, never on the server

## Server Availability States

Each MCP server entry in the `MCPServerTools` map reports one of two states:

```ts
// Available — server is connected and tools are discoverable
{
  status: "available",
  tools: Record<string, any>,
  client: MCPClient,
  config: MCPServerConfig
}

// Unavailable — connection failed, includes error details
{
  status: "unavailable",
  error: string,
  client: MCPClient | null,
  config: MCPServerConfig
}
```

When a server is unavailable, its tools are excluded from the AI's tool set, and the error message is surfaced in the Settings UI.
