Kubernetes provides enterprise-grade container orchestration with automatic scaling, self-healing, and declarative configuration. This guide covers migrating Amplify from the WebContainer workbench to a Kubernetes deployment.

## Kubernetes Deployment Concepts

Before diving into the configuration, understand how the key Kubernetes concepts map to Amplify's architecture:

```text
┌──────────────────────────────────────────────────────────┐
│                     Kubernetes Cluster                    │
│                                                           │
│  ┌─────────────┐  ┌─────────────┐  ┌──────────────────┐  │
│  │ Deployment   │  │ Service     │  │ Ingress          │  │
│  │ (Amplify    │  │ (ClusterIP  │  │ (External access │  │
│  │  Pods)      │  │  or LB)     │  │  + SSL)          │  │
│  └─────────────┘  └─────────────┘  ┌──────────────────┘  │
│                                                           │
│  ┌─────────────┐  ┌─────────────┐  ┌──────────────────┐  │
│  │ ConfigMap   │  │ Secrets     │  │ Persistent       │  │
│  │ (Non-secret │  │ (API keys)  │  │ Volume           │  │
│  │  config)   │  │             │  │ (Data storage)   │  │
│  └─────────────┘  └─────────────┘  └──────────────────┘  │
│                                                           │
│  ┌─────────────────────────────────────────────────────┐  │
│  │ Horizontal Pod Autoscaler (HPA)                     │  │
│  │ Auto-scaling based on CPU/memory metrics            │  │
│  └─────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────┘
```

## Creating a Deployment Manifest

The Deployment manages Amplify's pod lifecycle:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: amplify
  labels:
    app: amplify
spec:
  replicas: 2
  selector:
    matchLabels:
      app: amplify
  template:
    metadata:
      labels:
        app: amplify
    spec:
      containers:
        - name: amplify
          image: ghcr.io/amplify/amplify:latest
          ports:
            - containerPort: 5173
              protocol: TCP
          envFrom:
            - configMapRef:
                name: amplify-config
            - secretRef:
                name: amplify-secrets
          env:
            - name: RUNNING_IN_DOCKER
              value: "true"
            - name: NODE_ENV
              value: "production"
            - name: PORT
              value: "5173"
          resources:
            limits:
              memory: "2Gi"
              cpu: "2000m"
            requests:
              memory: "512Mi"
              cpu: "500m"
          livenessProbe:
            httpGet:
              path: /
              port: 5173
            initialDelaySeconds: 10
            periodSeconds: 15
            timeoutSeconds: 3
            failureThreshold: 5
          readinessProbe:
            httpGet:
              path: /
              port: 5173
            initialDelaySeconds: 5
            periodSeconds: 10
            timeoutSeconds: 3
            failureThreshold: 3
          volumeMounts:
            - name: amplify-data
              mountPath: /app/data
            - name: amplify-logs
              mountPath: /app/logs
      volumes:
        - name: amplify-data
          persistentVolumeClaim:
            claimName: amplify-data-pvc
        - name: amplify-logs
          persistentVolumeClaim:
            claimName: amplify-logs-pvc
```

Key configuration choices:

- **`replicas: 2`** — Start with two replicas for basic high availability
- **`image: ghcr.io/amplify/amplify:latest`** — Use the prebuilt image or build and push your own
- **`envFrom`** — Loads all ConfigMap and Secret keys as environment variables
- **`resources`** — Set explicit limits to prevent resource contention
- **`volumeMounts`** — Persistent storage for data and logs

## Service Configuration

The Service exposes Amplify within the cluster:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: amplify
  labels:
    app: amplify
spec:
  type: ClusterIP
  selector:
    app: amplify
  ports:
    - name: http
      port: 80
      targetPort: 5173
      protocol: TCP
```

This creates an internal ClusterIP service that routes traffic from port 80 to the container's port 5173. Other services within the cluster can reach Amplify at `amplify:80`.

### LoadBalancer Service (Cloud Deployments)

For cloud providers that support external load balancers:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: amplify-lb
spec:
  type: LoadBalancer
  selector:
    app: amplify
  ports:
    - name: http
      port: 80
      targetPort: 5173
```

This provisions an external IP address for direct access without an Ingress controller.

## ConfigMap for Environment Variables

Non-sensitive configuration is stored in a ConfigMap:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: amplify-config
data:
  DEFAULT_NUM_CTX: "32768"
  VITE_LOG_LEVEL: "info"
  PORT: "5173"
  WRANGLER_SEND_METRICS: "false"
  # Local provider URLs (use service names within the cluster)
  OLLAMA_API_BASE_URL: "http://ollama:11434"
```

### Modifying Configuration

To update non-secret configuration:

```bash
# Edit the ConfigMap directly
kubectl edit configmap amplify-config

# Or apply an updated YAML file
kubectl apply -f amplify-config.yaml

# Restart pods to pick up changes
kubectl rollout restart deployment amplify
```

## Secrets for API Keys

Sensitive data like API keys is stored in Kubernetes Secrets:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: amplify-secrets
type: Opaque
stringData:
  OPENAI_API_KEY: "sk-your-openai-key"
  ANTHROPIC_API_KEY: "your-anthropic-key"
  GROQ_API_KEY: "your-groq-key"
  GOOGLE_GENERATIVE_AI_API_KEY: "your-google-key"
  OPEN_ROUTER_API_KEY: "your-openrouter-key"
```

### Creating Secrets Securely

Avoid putting actual key values in YAML files. Use imperative commands instead:

```bash
kubectl create secret generic amplify-secrets \
  --from-literal=OPENAI_API_KEY=sk-your-openai-key \
  --from-literal=ANTHROPIC_API_KEY=your-anthropic-key \
  --from-literal=GROQ_API_KEY=your-groq-key
```

Or load from a file:

```bash
kubectl create secret generic amplify-secrets \
  --from-env-file=.env.local
```

## Ingress Configuration

The Ingress controller manages external access with SSL and routing:

### Basic Ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: amplify-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  rules:
    - host: amplify.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: amplify
                port:
                  number: 80
```

### Ingress with SSL (Let's Encrypt)

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: amplify-ingress
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    # WebSocket support for real-time features
    nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "3600"
spec:
  tls:
    - hosts:
        - amplify.example.com
      secretName: amplify-tls
  rules:
    - host: amplify.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: amplify
                port:
                  number: 80
```

The WebSocket annotations (`proxy-read-timeout` and `proxy-send-timeout`) are essential for Amplify's real-time features, including AI streaming responses and terminal interactions.

## Persistent Volumes for Data

### PersistentVolumeClaim Templates

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: amplify-data-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
  storageClassName: standard

---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: amplify-logs-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
  storageClassName: standard
```

### Storage Considerations

- **ReadWriteOnce** — Single pod access (suitable for single-replica deployments)
- **ReadWriteMany** — Multiple pod access (required for multi-replica deployments with shared data)
- Use a network-backed storage class (NFS, Ceph, EFS, etc.) for `ReadWriteMany`

For multi-replica deployments with shared project data, consider an external database or object store instead of filesystem persistence.

## Scaling Considerations

### Horizontal Pod Autoscaler

Automatically scale Amplify based on load:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: amplify-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: amplify
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
```

### Scaling Requirements

When scaling Amplify beyond a single replica:

1. **Session affinity**: Use session-affinity in the Service to ensure a user's requests consistently reach the same pod (important for WebContainer sessions)

```yaml
apiVersion: v1
kind: Service
metadata:
  name: amplify
spec:
  sessionAffinity: ClientIP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 3600    # 1-hour session stickiness
```

2. **Shared state**: Multi-replica deployments require shared state for:
   - Project data — Use a shared PVC or external storage (S3, NFS)
   - Vector store — Use an external vector database instead of in-memory Orama
   - Settings — Use an external database or shared configuration store

3. **AI provider rate limits**: Scaling increases concurrent API calls. Monitor rate limits for each provider and add backpressure or request queuing as needed.

## Health Checks and Probes

Kubernetes uses three types of probes to monitor pod health:

### Liveness Probe

Detects dead pods that need to be restarted:

```yaml
livenessProbe:
  httpGet:
    path: /
    port: 5173
  initialDelaySeconds: 10
  periodSeconds: 15
  timeoutSeconds: 3
  failureThreshold: 5
```

### Readiness Probe

Detects pods that are ready to serve traffic:

```yaml
readinessProbe:
  httpGet:
    path: /
    port: 5173
  initialDelaySeconds: 5
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3
```

### Startup Probe

For applications with slow initialization (large Node.js apps):

```yaml
startupProbe:
  httpGet:
    path: /
    port: 5173
  initialDelaySeconds: 0
  periodSeconds: 5
  failureThreshold: 30    # Allows up to 150 seconds for startup
```

The startup probe prevents the liveness probe from killing the pod during initialization. Once the startup probe succeeds, liveness and readiness probes take over.

## Step-by-Step Migration Instructions

### Step 1: Prepare the Cluster

```bash
# Verify cluster access
kubectl cluster-info

# Create a dedicated namespace
kubectl create namespace amplify
```

### Step 2: Build and Push the Image

```bash
# Build the production image
pnpm run dockerbuild:prod

# Tag for your registry
docker tag amplify-ai:production your-registry.com/amplify:latest

# Push to your registry
docker push your-registry.com/amplify:latest
```

Or use the prebuilt image:

```bash
# Pull the official image
docker pull ghcr.io/amplify/amplify:latest
```

### Step 3: Create Secrets

```bash
kubectl create secret generic amplify-secrets \
  --from-env-file=.env.local \
  -n amplify
```

### Step 4: Create ConfigMap

```bash
kubectl apply -f amplify-config.yaml -n amplify
```

### Step 5: Deploy

Apply all manifests:

```bash
kubectl apply -f amplify-deployment.yaml -n amplify
kubectl apply -f amplify-service.yaml -n amplify
kubectl apply -f amplify-pvc.yaml -n amplify
kubectl apply -f amplify-ingress.yaml -n amplify
```

Or use a single Kustomize or Helm configuration.

### Step 6: Verify the Deployment

```bash
# Check pod status
kubectl get pods -n amplify

# Check service endpoints
kubectl get svc -n amplify

# Check ingress
kubectl get ingress -n amplify

# Test the application
curl http://amplify.example.com
```

### Step 7: Set Up Auto-Scaling

```bash
kubectl apply -f amplify-hpa.yaml -n amplify

# Monitor scaling
kubectl get hpa -n amplify
```

### Step 8: Configure Monitoring

Set up monitoring and alerting:

```bash
# If using Prometheus
kubectl apply -f amplify-service-monitor.yaml -n amplify

# Check logs
kubectl logs -f deployment/amplify -n amplify
```

### Step 9: Migrate Workbench Data

Export projects from the WebContainer workbench and import them into your persistent volume:

```bash
# Copy exported project files to the persistent volume
kubectl cp projects.zip amplify/amplify-pod:/app/data/projects/
```

### Step 10: Ongoing Maintenance

```bash
# Update the deployment with a new image
kubectl set image deployment/amplify amplify=ghcr.io/amplify/amplify:v1.1.0 -n amplify

# Rollback if issues occur
kubectl rollout undo deployment/amplify -n amplify

# Check rollout status
kubectl rollout status deployment/amplify -n amplify
```
