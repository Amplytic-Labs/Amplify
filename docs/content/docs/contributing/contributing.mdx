Thank you for your interest in contributing to Amplify! This guide covers everything you need to know about submitting code, reporting bugs, and proposing new features.

## How to Contribute

### Fork and Branch

1. **Fork** the repository on GitHub
2. **Clone** your fork locally:

```bash
git clone https://github.com/your-username/open-claude.git
cd open-claude
```

3. **Create a feature branch** from `main`:

```bash
git checkout main
git pull origin main
git checkout -b feature/your-feature-name
```

Use descriptive branch names:
- `feature/add-mistral-provider`
- `fix/chat-streaming-error`
- `docs/extending-guide`

4. **Make your changes** and commit with clear messages:

```bash
git add .
git commit -m "feat: add Mistral provider with dynamic model discovery"
```

### Commit Message Format

We follow conventional commit prefixes:

| Prefix | Usage |
|--------|-------|
| `feat:` | New feature or capability |
| `fix:` | Bug fix |
| `docs:` | Documentation changes |
| `refactor:` | Code restructuring without behavior change |
| `test:` | Adding or updating tests |
| `chore:` | Build, config, or tooling changes |
| `style:` | Formatting, whitespace (no logic changes) |

### Push and Create a PR

```bash
git push origin feature/your-feature-name
```

Then open a Pull Request on GitHub targeting the `main` branch.

## Code Style and Formatting

### ESLint

Amplify uses ESLint with the `@blitz/eslint-plugin` config. Key rules:

- **No relative imports** — always use `~/` path aliases instead of `../`
- **Semicolons required** — all statements must end with `;`
- **Consistent return** — functions must consistently return or not return
- **Unix line breaks** — LF only, no CRLF
- **Curly braces required** — even for single-line blocks

Run ESLint:

```bash
pnpm lint
```

Fix auto-correctable issues:

```bash
pnpm lint:fix
```

### TypeScript

- All new files must use TypeScript (`.ts` or `.tsx`)
- Avoid `any` types where possible — use proper interfaces and generics
- Export types from dedicated `types.ts` files when they're shared across modules
- Use `z` from Zod for runtime validation schemas

### Naming Conventions

- **Components:** PascalCase (`ChatBox.tsx`, `ProjectSidebar.tsx`)
- **Utilities:** camelCase (`createScopedLogger.ts`, `normalizePath.ts`)
- **Constants:** UPPER_SNAKE_CASE (`WORK_DIR`, `DEFAULT_MODEL`)
- **Stores:** camelCase with `Store` suffix (`chatStore`, `themeStore`)
- **Providers:** PascalCase with `Provider` suffix (`OpenAIProvider`, `GroqProvider`)
- **Routes:** match Remix conventions (see [Adding Routes](/docs/extending/adding-routes))

### Prettier

Formatting is handled by Prettier. The project includes these settings:

- Single quotes for strings
- 2-space indentation
- Trailing commas where valid
- 120 character print width

Run Prettier:

```bash
pnpm format
```

### File Organization

```
app/
  components/        # React components
    chat/            # Chat-related components
    ui/              # Shared UI components
    workbench/       # Editor/preview components
  lib/               # Shared libraries
    modules/llm/     # LLM provider system
    services/        # Service classes (MCP, SkillLoader)
    stores/          # Nanostores state
    tools/           # Native tools
    vector-store/    # Orama vector stores
  routes/            # Remix route handlers
  utils/             # Utility functions
  types/             # TypeScript type definitions
```

## Testing Expectations

### Unit Tests

Amplify uses Vitest for unit tests. Test files follow the `.spec.ts` naming convention:

```ts
// app/lib/tools/nativeTools.spec.ts
import { describe, it, expect } from 'vitest';
import { buildNativeTools } from '~/lib/tools/nativeTools';

describe('read_file tool', () => {
  const tools = buildNativeTools();

  it('should read file content', async () => {
    const result = await tools.read_file.execute(
      { filePath: '/home/project/src/index.ts' },
      { files: mockFileMap },
    );
    expect(result).toContain('export default');
  });
});
```

Run tests:

```bash
pnpm test
```

Run a specific test file:

```bash
pnpm test app/lib/tools/nativeTools.spec.ts
```

### Test Requirements

When contributing:

- **Bug fixes** must include a test that reproduces the bug and verifies the fix
- **New features** should include basic tests for core functionality
- **Tools** must include tests in the corresponding `.spec.ts` file
- Tests should not rely on external APIs or services — mock them

### Snapshot Tests

Vitest supports snapshot testing for message parsing and other text-processing logic:

```ts
it('should parse messages correctly', () => {
  const result = parseMessage(input);
  expect(result).toMatchSnapshot();
});
```

## PR Review Process

### Before Submitting

1. **Run the full lint suite:** `pnpm lint`
2. **Run all tests:** `pnpm test`
3. **Test manually in the browser:** `pnpm dev`
4. **Update documentation** if your change affects public APIs

### PR Description

Include in your PR description:

- **What** — what the PR does
- **Why** — motivation and context
- **How** — implementation approach
- **Testing** — how you verified the change works
- **Screenshots** — for UI changes

### Review Criteria

Reviewers will check:

- Code follows style guidelines
- No regressions in existing functionality
- Tests cover the new behavior
- Documentation is updated if needed
- No unnecessary dependencies added
- TypeScript types are correct and complete

### Review Timeline

We aim to review PRs within 3–5 business days. Complex changes may take longer. You can ping maintainers on the PR if it hasn't received attention after a week.

## Issue Reporting

### Bug Reports

When reporting bugs, include:

1. **Environment** — OS, browser, Amplify version
2. **Steps to reproduce** — exact sequence that triggers the bug
3. **Expected behavior** — what should happen
4. **Actual behavior** — what actually happens
5. **Screenshots/logs** — visual evidence or error messages
6. **Configuration** — provider, model, MCP servers connected

Use the bug report template on GitHub Issues.

### Security Issues

**Do not report security vulnerabilities in public GitHub issues.** Instead, email security concerns to the maintainers directly or use GitHub's private vulnerability reporting feature.

## Feature Requests

### Proposal Process

1. **Check existing issues** — search for similar requests first
2. **Open a feature request issue** — describe the use case and expected behavior
3. **Wait for feedback** — maintainers will assess feasibility and alignment
4. **Get approval** — before writing code, confirm the feature is wanted
5. **Implement** — follow the standard PR process

### Good Feature Requests Include

- **Problem statement** — what current limitation exists
- **Proposed solution** — how you'd like it to work
- **Alternatives considered** — other approaches you've thought about
- **Use cases** — who would benefit and how
- **Scope** — is this a small addition or a major feature

### Areas We're Especially Interested In

- New LLM provider integrations
- Additional MCP server support
- Design system contributions
- Accessibility improvements
- Performance optimizations
- Mobile/responsive improvements

## Development Setup

### Quick Start

```bash
# Clone the repo
git clone https://github.com/Amplytic-Labs/open-claude.git
cd open-claude

# Install dependencies
pnpm install

# Set up environment
cp .env.example .env.local
# Edit .env.local with your API keys

# Start development server
pnpm dev
```

### Docker Setup

```bash
# Development with Docker
docker compose --profile development up

# Production build
docker compose --profile production up
```

### Environment Variables

Required for most development:

```bash
ANTHROPIC_API_KEY=your-key      # Default provider
OPENAI_API_KEY=your-key         # OpenAI provider
```

Optional per-provider keys:

```bash
GROQ_API_KEY=your-key
GOOGLE_GENERATIVE_AI_API_KEY=your-key
OPEN_ROUTER_API_KEY=your-key
XAI_API_KEY=your-key
DEEPSEEK_API_KEY=your-key
```
