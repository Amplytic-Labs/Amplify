# Planning

The Planning system is Amplify's approach to handling complex, multi-step tasks. Instead of trying to do everything in one long conversation, Amplify breaks tasks into structured plan points, enriches them with detailed Task Contracts, executes each point in an isolated context window, and verifies the results.

## execute_plan Tool

The AI can invoke the **`execute_plan`** tool when it determines that a task is too complex for a single response. This tool:

1. Accepts a **draft plan** — a list of plan points with titles and descriptions
2. Returns an `execute_plan_signal` that triggers the planning pipeline
3. The signal flows to `Chat.client.tsx`, which initiates enrichment and approval

The AI creates the draft plan based on the user's request, the project context, and its understanding of the required steps. Each point represents a discrete unit of work — for example, "Create the login screen component" or "Set up the authentication service."

## Planner LLM Enrichment

Once a draft plan is created, it's sent to a dedicated **Planner LLM** (via `/api/plan`) that enriches each point into a full **Task Contract**:

| Draft Field | Enriched Field | Description |
|-------------|----------------|-------------|
| `title` | `title` | Short, human-readable task name |
| `description` | `goal` | One or two sentences describing what "done" looks like |
| | `description` | Detailed implementation notes (becomes the worker's primary instruction) |
| | `requirements` | Explicit requirements the implementation must satisfy |
| | `successCriteria` | Used by verification to decide if the task is truly complete |
| | `requiredSkills` | Skills to invoke before the worker starts |
| | `requiredToolOutputs` | References to tool outputs to fetch and inject |
| | `expectedFiles` | Files this task is expected to create or modify |
| | `verificationChecks` | Checks to run after completion |
| | `constraints` | Boundaries (files not to modify, packages not to install) |

The planner also attaches **`plannerNotes`** — global guidance that every worker inherits.

If the planner call fails (network error, bad key, unparseable output), the system gracefully degrades: the original draft plan is shown unchanged, and the user can still approve and execute it.

## Sequential Plan Point Execution

After approval, each plan point is executed **sequentially** in order:

1. The **ExecutionManager** orchestrates the task queue
2. Each point transitions through statuses: `pending` → `preparing` → `in_progress` → `verifying` → `completed`
3. Points can have dependencies on earlier points — a point won't start until its dependencies complete
4. After each point completes, its results are extracted and stored in the **ProjectContextVectorStore** for subsequent points to access

This sequential approach ensures coherence: each worker sees the cumulative results of all previous work.

## Plan Approval Dialog

Before execution begins, the **PlanApprovalDialog** UI shows the enriched plan:

- Task description and planner notes at the top
- Each plan point listed with its goal, requirements, and expected files
- Expandable sections showing verification checks and constraints
- **Approve** or **Reject** buttons at the bottom
- A progress view tracks each point's status during execution

You can review exactly what the AI intends to do before any code is written.

## Sub-Chat Engine

Each plan point is executed as an **independent sub-chat** (worker) with its own context window. This is the key innovation of the planning system:

### Why Sub-Chats?

A single long conversation consumes enormous tokens — every tool call, every file read, every previous message stays in context. Sub-chats solve this by giving each worker a **fresh, lean context** containing only what it needs.

### Context Assembly

The **ContextBuilder** assembles each worker's context from four sources:

| Source | Content | Purpose |
|--------|---------|---------|
| **Task Contract** | Immutable contract: goal, requirements, success criteria | What to do |
| **Project Context** | Framework, architecture, file tree, vector store results | What exists |
| **Skills** | Only the required skills, loaded with structured output | How to do it |
| **Tool Outputs** | Resolved references from previous points | What's already done |

These are assembled into labeled sections: `TASK / PROJECT / SKILLS / TOOL RESULTS / WORKSPACE / CONSTRAINTS / USER REQUEST`.

### Checkpoints and Resume

Sub-chats support deterministic resume:

- **Checkpoints** are structured snapshots taken every N tool calls
- Each checkpoint records: files changed, tools used, progress summary, remaining work
- On interruption, the runtime reconstructs the worker's context from the latest checkpoint — no AI reasoning required
- This makes execution reliable even in long-running tasks

## Verification System

After each plan point completes, the **verification system** runs checks to ensure the implementation is correct:

### Lint Checker

Runs ESLint (or equivalent) on modified files to catch style errors, unused variables, and common mistakes.

### Type Checker

Runs the TypeScript compiler (or equivalent) on modified files to catch type errors, missing imports, and incorrect type annotations.

### Flow Verifier

Enforces two core rules:

1. **"Every button does something"** — scans for `onClick`, `onChange`, `onSubmit` handlers that are empty, call undefined functions, or are no-ops
2. **"Every screen is connected"** — scans route definitions and navigation to ensure newly created screens are reachable from existing navigation

### Build Check

Verifies that the project builds successfully after modifications.

### Verification Results

If verification fails:

1. Errors are sent back to the sub-chat as feedback
2. The worker attempts to fix the issues
3. Verification re-runs
4. If it still fails, the point is marked as `failed` with error details

Verification results are stored alongside each plan point and visible in the plan progress view.
