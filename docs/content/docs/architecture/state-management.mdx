Amplify uses a layered state management architecture that combines lightweight reactive atoms (Nanostores), structured persisted stores (Zustand), and two browser storage backends (IndexedDB and localStorage). Each layer serves a distinct purpose and the layers interact through well-defined patterns.

## Layer Overview

| Layer | Technology | Use Case | Persistence |
|-------|-----------|---------|------------|
| UI state | Nanostores (atoms/maps) | Toggles, flags, transient values | None (resets on reload) |
| Settings/config | Zustand | Structured settings, MCP, model config | localStorage |
| Chat history | IndexedDB | Messages, snapshots, project files | IndexedDB |
| Memories | MemoryStore (singleton) | User preferences, context hints | localStorage |

## Nanostores — Lightweight State

Nanostores provide the fastest, most minimal reactive primitives. They're used for UI-level state that doesn't need persistence — values that should reset on page reload or are derived from other sources.

### Atoms (single values)

```ts
// Streaming flag — is the LLM currently generating?
export const streamingState = atom<boolean>(false);

// Model thinking/reasoning config — persisted separately via localStorage
export const modelConfigStore = atom<ModelConfigStore>({ ... });

// Chat metadata — set from IndexedDB on load
export const chatId = atom<string | undefined>(undefined);
export const description = atom<string | undefined>(undefined);
export const chatMetadata = atom<IChatMetadata | undefined>(undefined);

// Workbench UI state
workbenchStore.showWorkbench = atom(false);
workbenchStore.currentView = atom('code');
workbenchStore.unsavedFiles = atom(new Set<string>());
workbenchStore.actionAlert = atom<ActionAlert | undefined>(undefined);
```

### Maps (key-value dictionaries)

```ts
// Chat lifecycle state
export const chatStore = map({
  started: false,
  aborted: false,
  showChat: true,
});

// Workbench artifacts (running actions)
workbenchStore.artifacts = map<Record<string, ArtifactState>>({});

// Chat list version — bumped on every mutation for reactive sidebar updates
export const chatListVersion = atom(0);
```

### Why Nanostores for UI State?

- **Sub-microsecond updates** — no middleware, no selectors, just a value change
- **No boilerplate** — `atom(value)` and `map({})` are the entire API
- **React integration** — `useStore(atom)` from `@nanostores/react` provides a clean hook
- **Vite HMR support** — atoms can be preserved across hot module reloads via `import.meta.hot.data`

### HMR Pattern

Nanostores in the WorkbenchStore use a pattern that preserves state across Vite HMR updates:

```ts
showWorkbench: WritableAtom<boolean> =
  import.meta.hot?.data.showWorkbench ?? atom(false);

if (import.meta.hot) {
  import.meta.hot.data.showWorkbench = this.showWorkbench;
}
```

This means the workbench state (open panels, current view, file history) survives code changes during development.

## Zustand — Structured Settings Stores

Zustand is used for state that is:
- Structured (nested objects, arrays)
- Persisted across reloads
- Shared across multiple components
- Updated via async operations (API calls)

### useSettingsStore

The main settings store (`app/lib/stores/settings.ts`) manages:

| Slice | What it holds |
|-------|--------------|
| `providersStore` | Per-provider config (enabled, API key, base URL) |
| `shortcutStore` | Keyboard shortcuts (theme toggle, terminal toggle) |
| `tabConfigurationStore` | Workbench tab layout preferences |

Provider settings follow a layered initialization:

1. **Defaults** — each provider starts with `enabled: true` (except local providers like Ollama/LMStudio)
2. **localStorage merge** — saved settings override defaults
3. **Server auto-detect** — `/api.configured-providers` checks if env keys are set, auto-enables those providers
4. **Persist** — every change writes back to localStorage immediately

### useMCPStore

The MCP store (`app/lib/stores/mcp.ts`) manages Model Context Protocol server configuration:

```ts
const useMCPStore = create<Store & Actions>((set, get) => ({
  isInitialized: false,
  settings: { maxLLMSteps: 5, mcpConfig: { mcpServers: {} } },
  serverTools: {},  // Discovered tools per server
  error: null,
  isUpdatingConfig: false,

  initialize: async () => {
    // Read from localStorage → validate → POST to server → discover tools
  },

  updateSettings: async (settings) => {
    // Update store → persist to localStorage → POST to server
  },
}));
```

### useRateLimitStore

The rate limit store (`app/lib/stores/rate-limit.ts`) manages per-provider RPM/TPM/RPD limits. It uses localStorage persistence and sends the config to the server on each chat request via the `rateLimits` field.

## IndexedDB Persistence Layer

IndexedDB is the primary storage backend for chat data and project files. The database (`amplifyHistory`) has evolved through 4 schema versions.

### Object Stores

| Store | KeyPath | Schema Version | Contents |
|-------|---------|---------------|---------|
| `chats` | `id` | v1 | Chat messages, urlId, description, timestamp, metadata |
| `snapshots` | `chatId` | v2 | Per-chat FileMap snapshots (legacy, pre-project era) |
| `project_files` | `projectId` | v3 | Global, per-project current FileMap |
| `project_commits` | `id` (indexed by `projectId`) | v3 | Versioned snapshots of a project's files |
| `project_screenshots` | `projectId` | v4 | One PNG data URL per project (auto-replaced on capture) |

### Schema Migration

`openDatabase()` handles migrations in `onupgradeneeded`:

```
v1 → create chats store (id, urlId indexes)
v2 → create snapshots store (chatId keyPath)
v3 → create project_files + project_commits stores
v4 → create project_screenshots store
```

All migrations are additive — existing stores are never modified, only new ones are created. This ensures backward compatibility.

### Core Operations

| Function | Purpose |
|----------|---------|
| `setMessages(db, id, messages, urlId, description, timestamp, metadata)` | Write/update a chat record |
| `getMessages(db, id)` | Read by id (falls back to urlId) |
| `getAll(db)` | List all chats (sidebar rendering) |
| `deleteById(db, id)` | Delete a chat + its snapshot |
| `forkChat(db, chatId, messageId)` | Fork at a specific message |
| `duplicateChat(db, id)` | Full chat copy |
| `getSnapshot(db, chatId)` | Read a FileMap snapshot |
| `setSnapshot(db, chatId, snapshot)` | Write a snapshot |

## localStorage Persistence

localStorage is used for settings and config that are:
- Small (under 5MB total)
- Frequently read/written (every UI toggle)
- Not chat data (that belongs in IndexedDB)

### Storage Keys

| Key | Store | Contents |
|-----|-------|---------|
| `provider_settings` | SettingsStore | Per-provider enabled/baseUrl/apiKey |
| `auto_enabled_providers` | SettingsStore | Track which providers were auto-enabled |
| `mcp_settings` | MCPStore | MCP server config + maxLLMSteps |
| `amplify:model-config` | ModelConfigStore | Thinking/reasoning settings per model |
| `amplify:rate-limit` | RateLimitStore | Per-provider RPM/TPM/RPD limits |
| `amplify_user_memories` | MemoryStore | User preference memories |
| `theme` | ThemeStore | Light/dark theme preference |

### Helper Functions

`localStorage.ts` provides two simple helpers:

```ts
function getLocalStorage(key: string): any | null {
  // Parse JSON from localStorage, return null on error or missing
}

function setLocalStorage(key: string, value: any): void {
  // Serialize to JSON and write to localStorage
}
```

Both helpers guard against SSR (`typeof window !== 'undefined'`) and swallow errors (localStorage can be full or disabled).

## How Persistence Works

### Auto-Save

Every Zustand store auto-saves to localStorage on every mutation. This is done inline in the store's actions, not via middleware:

```ts
updateSettings: (settings) => {
  set({ settings });
  localStorage.setItem(MCP_SETTINGS_KEY, JSON.stringify(settings));
}
```

This is intentional — it avoids the overhead of Zustand middleware and ensures persistence is always in sync with the store state.

### Auto-Restore

Stores restore from localStorage during initialization:

1. **Zustand stores** — read `localStorage.getItem(key)` in `initialize()` or at module load time
2. **Nanostores** — `modelConfigStore` reads `localStorage.getItem('amplify:model-config')` on first access via a `hydrate()` function
3. **IndexedDB** — `useChatHistory` opens the database at module level (`const db = await openDatabase()`) and loads the current chat on mount

### IndexedDB Initialization

`useChatHistory` is the main hook that bridges IndexedDB and the React lifecycle:

```ts
const db = persistenceEnabled ? await openDatabase() : undefined;
```

On mount:
1. `openDatabase()` opens `amplifyHistory` v4
2. `getAll(db)` loads the chat list for the sidebar
3. `getMessages(db, chatId)` loads the current chat's messages
4. `getSnapshot(db, chatId)` restores the FileMap into the WebContainer

On every message update:
1. `setMessages(db, id, messages)` writes the full message array
2. `chatListVersion` atom is bumped to trigger sidebar re-render

## Store Hierarchy and Dependencies

The stores form a dependency graph with clear data flow direction:

```
useChatHistory (IndexedDB)
  ├─→ chatId atom
  ├─→ description atom
  ├─→ chatMetadata atom
  ├─→ chatListVersion atom
  └─→ workbenchStore (FileMap → WebContainer)

Chat.client.tsx
  ├─→ modelConfigStore (thinking config → server request)
  ├─→ rateLimitStore (limits → server request)
  ├─→ streamingState atom (UI indicator)
  ├─→ chatStore map (started/aborted flags)
  ├─→ useSettingsStore (provider selection → server request)
  └─→ useMCPStore (tool definitions → server request)

workbenchStore (Nanostores)
  ├─→ FilesStore → webcontainer (read/write files)
  ├─→ EditorStore → FilesStore (document state)
  ├─→ TerminalStore → webcontainer (shell commands)
  ├─→ PreviewsStore → webcontainer (preview URL)
  └─→ ActionRunner → webcontainer (mutation execution)

planStore (IndexedDB)
  ├─→ Plan points → SubChatEngine (worker execution)
  ├─→ Checkpoints → ContextBuilder (resume context)
  └─→ Verification → Runner (lint/type-check)

projectStore (IndexedDB)
  ├─→ project_files → workbenchStore (FileMap)
  ├─→ project_commits → version snapshots
  └─→ project_screenshots → sidebar thumbnails
```

### Data Flow Summary

- **User action** → Zustand/Nanostore update → localStorage auto-save → React re-render
- **Chat message** → IndexedDB write → chatListVersion bump → sidebar refresh
- **Model selection** → modelConfigStore update → localStorage persist → next request includes config
- **Provider toggle** → useSettingsStore update → localStorage persist → next model list fetch includes/excludes provider
- **Mutation execution** → ActionRunner → WebContainer → FilesStore refresh → workbenchStore re-render
