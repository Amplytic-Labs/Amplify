Amplify is an open-source AI-powered coding environment built on a **client-first architecture**: most state lives in the browser, the server acts as a thin streaming proxy for LLM APIs, and the entire editing + preview loop runs client-side inside a WebContainer.

## Tech Stack

| Layer | Technology | Purpose |
|-------|-----------|---------|
| Framework | Remix v2 with Vite | SSR/hydration, file-based routing, action loaders |
| Deployment | Cloudflare Pages / Wrangler | Edge deployment, serverless functions |
| Chat Streaming | Vercel AI SDK v7 | `useChat`, `streamText`, `UIMessage` streaming protocol |
| State (lightweight) | Nanostores (atoms/maps) | Chat status, streaming flag, UI toggles |
| State (structured) | Zustand | Settings, MCP config, model config |
| Persistence | IndexedDB + localStorage | Chat history, project files, provider keys |
| Styling | UnoCSS + SCSS modules | Atomic CSS + component-scoped styles |
| UI Primitives | Radix UI | Accessible Dialog, Popover, Tabs, Collapsible |
| Runtime | WebContainer API | In-browser Node.js for file ops + terminal |

## Client-First Philosophy

The core design principle is that **the browser is the primary runtime**. The server never stores user data, never manages sessions, and never writes files. Every interaction follows this loop:

1. **User sends a message** → client POSTs to `api.chat`
2. **Server streams LLM response** → thin proxy, no business logic
3. **Client parses mutations** → `MessageParser` extracts `<amplifyAction>` signals
4. **ActionRunner applies mutations** → writes files to WebContainer, runs shell commands
5. **WebContainer updates** → preview re-renders in the iframe

The server is deliberately kept stateless so it can run on Cloudflare Workers (edge, cheap, fast). All "intelligence" lives client-side.

## The Mutation Signal Pattern

Amplify doesn't let the LLM directly modify files. Instead, the LLM emits **structured JSON signals** (called mutations) inside its streamed response. These signals are parsed and applied client-side.

The flow:

```
LLM stream → <amplifyAction> JSON signal → MessageParser → ActionRunner → WebContainer
```

**Why this pattern?**
- The server never touches user files — it only proxies the LLM stream
- The client can intercept, approve, or reject mutations before execution
- Tool calls (file write, shell command) are rendered as UI cards before execution
- The user can see *what will happen* before it happens (with `TOOL_EXECUTION_APPROVAL`)

Mutation types include:
- **File actions** — create, update, delete files in the WebContainer
- **Shell actions** — run commands (`npm install`, `npm run dev`)
- **Start actions** — bootstrap a project from a template

## Progressive Skill Loading

Skills are markdown-based expert instructions loaded **on demand**. The `SkillLoader` service:

1. Reads available skills from `app/lib/skills/*/SKILL.md` and `design/design-systems/*/DESIGN.md`
2. Injects relevant skill content into the LLM's system prompt
3. Uses a **token budget** to avoid overflowing the context window — only skills the planner deems necessary are loaded

This keeps the system prompt lean (a few hundred tokens vs. dumping every skill) while still giving the LLM access to domain-specific expertise (React best practices, design system rules, etc.) when it needs it.

## Context Budget System

Amplify uses a token-aware context budget system instead of fixed message-count limits. The system:

1. **Reserves** 8,192 tokens for the system prompt (`SYSTEM_PROMPT_RESERVE`)
2. **Estimates** the current conversation's token footprint using a `chars/4` heuristic
3. **Calculates** the usable budget: `maxTokenAllowed − maxCompletionTokens − systemPromptReserve`
4. **Triggers summarization** at 70% of the usable budget (`SUMMARIZATION_THRESHOLD`)
5. **Auto-shrinks** older messages when rate limits demand it

This means a 16k-context model summarizes on turn 3, while a 1M-context Gemini model may never summarize at all — the right behavior for each model, without hard-coded thresholds.

## Planning with Sub-Chats

For complex multi-step tasks, Amplify uses a **planning architecture** that decomposes work into independent sub-chats:

1. **Planner AI** creates a `Plan` with ordered `PlanPoint`s
2. Each `PlanPoint` is executed as an **independent sub-chat** (worker) with its own context window
3. Workers receive assembled context from four sources:
   - **Task Context** — immutable contract (what to do)
   - **Project Context** — framework, architecture, file tree
   - **Skill Context** — structured outputs from relevant skills
   - **Runtime Context** — resolved tool output references
4. **Checkpoints** track progress every N tool calls (deterministic resume after interruption)
5. **Verification** runs lint, type-check, and flow checks after each point
6. Results are extracted and stored in a **ProjectContextVectorStore** for the next point

This dramatically reduces token consumption (each worker gets a focused context, not the entire conversation history) while maintaining coherence through vector-store-backed context sharing.

## SSR Considerations

Amplify uses Remix v2 with Cloudflare Workers, which means:

- **SSR shell** — the HTML shell (header, sidebar layout) is rendered server-side for fast initial load
- **Client hydration** — `Chat.client.tsx` and `Workbench.client.tsx` are `.client.tsx` files that only run in the browser
- **Server-only modules** — `.server/` directories are excluded from the client bundle (LLM code, API keys, system prompts never reach the browser)
- **Edge deployment** — Cloudflare Workers run the Remix action loaders at the edge, close to the user
- **No server-side state** — the Workers runtime has no persistent storage; all state is client-side
