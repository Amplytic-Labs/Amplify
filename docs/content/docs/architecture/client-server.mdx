---
title: Client-Server Architecture
description: How Amplify splits responsibilities between the browser runtime and the edge server.
---

Amplify is designed around a **thin server, thick client** model. The server runs on Cloudflare Workers (edge) and handles only Remix routing and LLM API proxying. The client is a full React application that manages state, persistence, file editing, and preview rendering entirely in the browser.

## The Client Side

### React Application Shell

The client is a Remix v2 + Vite React app that hydrates from an SSR shell. Key client-only components use the `.client.tsx` suffix to ensure they never run on the server:

- **`Chat.client.tsx`** — the main chat interface, uses `useChat` from Vercel AI SDK v7
- **`Workbench.client.tsx`** — the editor + preview + terminal panel
- **`ProjectSidebar.tsx`** — chat history sidebar

### State Stores

The client uses two state management systems:

**Nanostores** (lightweight atoms/maps) for UI-level state:
- `chatStore` — `{ started, aborted, showChat }`
- `streamingState` — boolean flag for whether a stream is active
- `workbenchStore.showWorkbench` — toggle the workbench panel
- `modelConfigStore` — thinking/reasoning config per model (persisted to localStorage)

**Zustand** for structured, persisted state:
- `useSettingsStore` — provider settings, API keys, theme, tab config
- `useMCPStore` — MCP server configuration and tool discovery
- `useRateLimitStore` — per-provider RPM/TPM/RPD limits

### WebContainer Runtime

The WebContainer API provides an in-browser Node.js runtime that runs the user's project. The `webcontainer` singleton is booted once on first client load:

```ts
webcontainer = WebContainer.boot({
  coep: 'credentialless',
  workdirName: WORK_DIR_NAME,
  forwardPreviewErrors: true,
});
```

The `ActionRunner` class is the bridge between LLM mutations and the WebContainer:
- File actions → `webcontainer.fs.writeFile()`
- Shell actions → `webcontainer.spawn()` (runs `npm install`, `npm run dev`, etc.)
- Start actions → template injection + auto-setup

### Persistence (IndexedDB + localStorage)

All user data is stored client-side:

| Storage | What it holds |
|---------|--------------|
| IndexedDB `chats` store | Chat messages, metadata, urlId |
| IndexedDB `snapshots` store | Per-chat FileMap snapshots |
| IndexedDB `project_files` store | Per-project current FileMap |
| IndexedDB `project_commits` store | Versioned commits of project files |
| IndexedDB `project_screenshots` store | One screenshot per project |
| localStorage | Provider settings, API keys, MCP config, model config, theme |

The `useChatHistory` hook manages the full lifecycle:
- Opens the IndexedDB database (`openDatabase()` → `amplifyHistory` v4)
- Reads/writes chat records via `setMessages()`, `getMessages()`
- Forks, duplicates, and deletes chats
- Tracks chat list version with `chatListVersion` atom for reactive updates

## The Server Side

### Remix Routes on Cloudflare Workers

The server runs as Cloudflare Pages Functions (Remix v2 action/loader pattern). Each route is a separate edge function:

| Route | Purpose |
|-------|---------|
| `api.chat` | Main streaming chat endpoint (POST) |
| `api.models` | Returns available model list (GET) |
| `api.models.$provider` | Per-provider model listing |
| `api.plan` | Planning endpoint for sub-chat execution |
| `api.enhancer` | Prompt enhancement |
| `api.llmcall` | Direct LLM call (for summarization) |
| `api.test-provider` | Provider connectivity test |
| `api.configured-providers` | Returns which providers have keys set |
| `api.web-search` | Web search proxy |
| `api.health` | Health check endpoint |
| `api.check-env-key` | Check if an env key is set |

### The `api.chat` Action

This is the most important server route. Its flow:

1. **Parse request** — extract messages, files, promptId, model/provider from POST body
2. **Context budget check** — `shouldSummarize()` estimates if the conversation exceeds the model's context window
3. **Summarization** (if needed) — `createSummary()` runs an LLM call to compress earlier messages
4. **Select context** — `selectContext()` chooses relevant workspace files to inject into the system prompt
5. **Stream response** — `streamText()` calls the Vercel AI SDK's `streamText()` with the selected model + tools + context
6. **Return streaming response** — `createUIMessageStreamResponse()` wraps the stream for the client

The server never stores messages, never writes files, and never manages sessions. It's a pure streaming proxy.

### Server-Only Modules

Code in `app/lib/.server/` is excluded from the client bundle by Remix's server-only convention. This includes:
- `llm/stream-text.ts` — the streaming handler
- `llm/context-budget.ts` — token estimation and summarization triggers
- `llm/rate-limit.ts` — pre-flight checks, throttle, auto-shrink
- `llm/create-summary.ts` — the summarization LLM call
- `llm/thinking.ts` — per-provider reasoning config translation
- `llm/select-context.ts` — workspace file selection for system prompt

### SSR Shell Rendering

`entry.server.tsx` renders the initial HTML shell (header, sidebar layout, theme) using `renderToReadableStream()`. The `themeStore` value is injected into the `<html data-theme>` attribute for instant dark/light mode without a flash.

## The API Route Structure

### Chat Flow Detail

The `api.chat` endpoint processes each turn:

```
Client POST → api.chat action
  → parseCookies() → extract API keys from cookie header
  → extract model/provider from last user message
  → contextBudget: shouldSummarize()
    → if yes: createSummary() → inject summary into system prompt
  → selectContext() → pick relevant files from workspace
  → preFlightCheck() → RPM/TPM/RPD rate limit enforcement
    → if auto-shrink: shrinkMessagesToFit() → drop older messages
  → streamText() → call LLM with tools, context, thinking config
  → createUIMessageStreamResponse() → return streaming response
```

Progress annotations are sent inline:
- `writeProgress()` — sends `{ type: 'progress', data: { message, status } }`
- `writeAnnotation()` — sends `{ type: 'data-annotation', data: { chatSummary, contextFiles } }`

### Model Listing

`api.models` and `api.models.$provider` use `LLMManager` to merge static + dynamic model lists:

```
GET /api.models → LLMManager.getModelList()
  → static models (hardcoded in each provider)
  → dynamic models (fetched from provider APIs)
  → merge: dynamic overrides static (e.g. Gemini 4's real 256k context vs. hardcoded 128k)
  → cache per-provider (keyed on apiKey + baseUrl + settings)
```

## How Mutations Flow

The complete mutation lifecycle:

1. **LLM emits tool call** — the AI SDK streams a tool invocation (e.g. `writeFile`, `shellCommand`)
2. **Client receives tool part** — `Chat.client.tsx` detects tool parts via `isToolPart()`
3. **Tool approval** — if `TOOL_EXECUTION_APPROVAL` is enabled, the UI shows a confirmation dialog
4. **ActionRunner executes** — `ActionRunner.runAction()` dispatches to:
   - File actions → `webcontainer.fs.writeFile()` / `webcontainer.fs.mkdir()`
   - Shell actions → `webcontainer.spawn()` with abort signal
   - Start actions → template bootstrap + `npm install` + `npm run dev`
5. **WorkbenchStore updates** — `filesStore` refreshes the file tree, `previewsStore` updates the preview URL
6. **UI re-renders** — React components subscribed to Nanostore atoms re-render

### Native Tools (Vercel AI SDK v7)

Amplify uses Vercel AI SDK v7's native tool system. Tools are defined in `stream-text.ts` and executed on the server:

| Tool | Purpose | Server-side? |
|------|---------|-------------|
| `read_file` | Read a file from workspace | Yes — needs file content in context |
| `write_file` | Write a file to workspace | No — streamed as signal, client applies |
| `shell_command` | Run a terminal command | No — streamed as signal, client runs in WebContainer |
| `web_search` | Search the web | Yes — fetches results, injects into context |
| `inject_template` | Bootstrap a project template | No — client-side template injection |
| `list_files` | List workspace file tree | Yes — needs paths for context selection |

Server-side tools produce results that are injected into the LLM's next step. Client-side tools produce mutation signals that are parsed and applied by `ActionRunner`.

## WebSocket / Real-Time Aspects

Amplify does not use WebSocket connections. All real-time communication uses:

1. **HTTP streaming** — the `api.chat` endpoint returns a `UIMessageStream` (text/event-stream) that the client consumes via `useChat`
2. **Server-Sent Events pattern** — the Vercel AI SDK's `createUIMessageStreamResponse()` encodes tool calls, text deltas, and annotations as SSE-like data chunks
3. **WebContainer internal events** — `webcontainer.on('server-ready')` fires when `npm run dev` starts, triggering preview URL updates

The `SwitchableStream` class allows the server to switch between the LLM stream and in-process annotations (progress, context budget info) without breaking the client's stream consumer.

## SSR Considerations

### Client-Only Components

Components that require browser APIs (IndexedDB, WebContainer, localStorage) use the `.client.tsx` suffix. Remix excludes these from the server bundle and they hydrate after the initial SSR shell renders.

### Server-Only Modules

The `.server/` directory convention ensures LLM code never reaches the client:
- `app/lib/.server/llm/*` — streaming, rate limiting, summarization, thinking config
- These modules are stripped from the Vite client build via Remix's server-only detection

### Environment Variables

Cloudflare Workers use `env` bindings (set in `wrangler.toml`) instead of `process.env`. The `BaseProvider.getProviderBaseUrlAndKey()` method resolves keys from multiple sources in priority order:

```
apiKeys (from cookies) → providerSettings.baseUrl → serverEnv → process.env → LLMManager.env → config.baseUrl
```

This allows API keys to come from:
- Client-side cookies (user's own keys)
- Cloudflare Worker env bindings (server-side keys)
- `process.env` (local development)
