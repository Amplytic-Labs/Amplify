## Overview

Amplify offers an **Electron-based desktop app** that wraps the web application with native system integration. The desktop app provides operating-system-level features that are impossible in a browser context: native menus, auto-update, system tray, and local file access without COOP/COEP restrictions.

## Features

| Feature              | Description                                                           |
|----------------------|-----------------------------------------------------------------------|
| **Native menus**     | Application menu bar with Back/Forward navigation shortcuts           |
| **Auto-update**      | Automatic checking for updates every 4 hours with user-prompted installs |
| **Cookie persistence**| Session cookies survive across app restarts via ElectronStore         |
| **Local protocol**   | Custom `http://` protocol handler for serving the app locally         |
| **Window management**| Standard macOS/Windows/Linux window behaviors (minimize, dock, etc.)  |
| **Dev/prod modes**   | Vite dev server in development; self-hosted Remix build in production |

## Installation

### Download Binaries

Pre-built binaries are available from **GitHub Releases**:

- **macOS**: `.dmg` installer (signed with hardened runtime)
- **Windows**: `.exe` NSIS installer with optional custom install directory
- **Linux**: `.AppImage` (portable) and `.deb` (Debian/Ubuntu package)

Visit the [releases page](https://github.com/Derek-X-Wang/amplify/releases) to download the latest version.

### Building from Source

The desktop app is built using **electron-builder** with the configuration in `electron-builder.yml`.

```bash
# Build the Remix server and client bundles
npm run build

# Package the Electron app
npx electron-builder
```

The build process:

1. Compiles the Remix server build (`build/server/`) and client build (`build/client/`)
2. Compiles the Electron main process (`build/electron/main/`) and preload script (`build/electron/preload/`)
3. Packages everything into an ASAR archive with unpacked resources
4. Produces platform-specific installers (DMG, NSIS, AppImage, DEB)

## electron-builder.yml Configuration

```yaml
appId: com.amplify.dev
productName: Amplify
directories:
  buildResources: build
  output: dist
files:
  - build/**/*
  - package.json
  - node_modules/**/*
  - icons/**
  - electron-update.yml
extraMetadata:
  main: build/electron/main/index.mjs

mac:
  icon: assets/icons/icon.icns
  target: dmg
  hardenedRuntime: true
  entitlements: assets/entitlements.mac.plist
  category: public.app-category.developer-tools

win:
  icon: assets/icons/icon.ico
  target: nsis

linux:
  icon: assets/icons/icon.png
  target:
    - AppImage
    - deb
  category: Development

publish:
  provider: github
  owner: Derek-X-Wang
  repo: amplify
  releaseType: release
```

Key configuration points:

- **`asarUnpack`** — Server build and resources are unpacked from the ASAR archive for direct file access
- **`hardenedRuntime`** — macOS security requirement for notarization
- **`nsis`** — Windows installer supports custom installation directory and desktop/start menu shortcuts

## Auto-Update via electron-updater

The desktop app checks for updates automatically using **electron-updater**:

```ts
// Checks on startup and every 4 hours
setInterval(() => autoUpdater.checkForUpdates(), 4 * 60 * 60 * 1000);
```

### Update Flow

1. **Check** — `autoUpdater.checkForUpdates()` queries the GitHub Releases API
2. **Notify** — If an update is available, a dialog prompts the user: "Version X is available. Update now?"
3. **Download** — If the user chooses "Update", the new version downloads in the background
4. **Install** — After download, another dialog offers "Restart" or "Later"
5. **Apply** — On restart, the new version is installed via `quitAndInstall()`

The auto-updater configuration:

- `autoDownload: false` — Updates are not downloaded automatically; user consent is required
- `autoInstallOnAppQuit: true` — Pending updates install on next app quit
- `updateConfigPath` — Points to `electron-update.yml` for custom update server configuration

### Update Configuration

The `electron-update.yml` file controls the update provider:

```yaml
provider: github
owner: Derek-X-Wang
repo: amplify
private: true
releaseType: release
```

## macOS Notarization

For macOS distribution, the app must be **notarized** with Apple. The electron-builder config includes:

- `hardenedRuntime: true` — Required for notarization
- `entitlements: assets/entitlements.mac.plist` — macOS entitlements file
- `gatekeeperAssess: false` — Disables Gatekeeper assessment during build
- `identity: null` — Uses the default signing identity

Notarization is handled by electron-builder during the packaging step when Apple Developer credentials are available.

## Architecture

The Electron app follows a standard main/preload/renderer architecture:

```
┌──────────────────────────┐
│  Main Process (index.ts) │
│  ├─ App lifecycle        │
│  ├─ Protocol handler     │
│  ├─ Auto-updater         │
│  ├─ Menu setup           │
│  ├─ Cookie management    │
│  └────────────────────── │
└──────────┬───────────────┘
           │ IPC
           ▼
┌──────────────────────────┐
│  Preload (index.ts)      │
│  └─ Bridge APIs          │
└──────────┬───────────────┘
           │
           ▼
┌──────────────────────────┐
│  Renderer (Remix app)    │
│  └─ Same web app code    │
└──────────────────────────┘
```

### Main Process

The main process (`electron/main/index.ts`) handles:

- **Protocol handling** — Intercepts `http://localhost:{port}` requests and routes them through Remix's server build in production, or Vite's dev server in development
- **Cookie persistence** — Loads cookies from ElectronStore on startup and stores them back on each request, ensuring session persistence across restarts
- **IPC** — Basic ping/ipcTest channels for main↔renderer communication

### Dev vs. Production Mode

```ts
if (isDev) {
  // Development: forward all requests to Vite dev server
  await initViteServer();
  return await fetch(req);
} else {
  // Production: serve static assets first, then Remix handler
  const assetRes = await serveAsset(req, assetPath);
  if (assetRes) return assetRes;
  const handler = createRequestHandler(serverBuild, 'production');
  return await handler(req, { cloudflare: {} });
}
```

In production, the main process acts as a mini-web-server, serving the Remix app's static assets and server-rendered routes locally — no external server needed.
