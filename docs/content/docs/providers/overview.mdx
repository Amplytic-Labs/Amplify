Amplify ships with **22+ AI providers** out of the box, ranging from cloud-hosted APIs (OpenAI, Anthropic, Google) to local inference engines (Ollama, LM Studio). Every provider follows the same `BaseProvider` architecture, making it straightforward to add new providers or configure existing ones.

## Supported Providers

| Category | Providers |
|----------|-----------|
| **Cloud** | Anthropic, OpenAI, Google, Groq, xAI, DeepSeek, Mistral, Cohere, Together, Perplexity, HuggingFace, OpenRouter, Amazon Bedrock, Cerebras, Fireworks, Moonshot, Hyperbolic, GitHub Models, Z.AI |
| **Local** | Ollama, LM Studio, OpenAI-like |
| **Custom** | Any OpenAI-compatible endpoint (via UI or code) |

## Provider Architecture

Every provider extends the abstract `BaseProvider` class located in `app/lib/modules/llm/base-provider.ts`. This class defines the contract that the `LLMManager` uses to register, discover, and instantiate models.

### BaseProvider Contract

```typescript
abstract class BaseProvider implements ProviderInfo {
  abstract name: string;           // Unique provider identifier
  abstract staticModels: ModelInfo[];  // Hardcoded fallback models
  abstract config: ProviderConfig;     // API key / base URL env var names

  // Optional: fetch models from the provider's API at runtime
  getDynamicModels?(...): Promise<ModelInfo[]>;

  // Required: create a model instance for the AI SDK
  abstract getModelInstance(options): LanguageModel;
}
```

### ProviderConfig

Each provider declares which environment variables hold its API key and (optionally) its base URL:

```typescript
interface ProviderConfig {
  baseUrlKey?: string;    // e.g. 'OLLAMA_API_BASE_URL'
  baseUrl?: string;       // Hardcoded default, e.g. 'http://localhost:1234/'
  apiTokenKey?: string;   // e.g. 'ANTHROPIC_API_KEY'
}
```

The `getProviderBaseUrlAndKey` method resolves the actual values from multiple sources (user settings, server env, process env, manager env) in priority order.

### ModelInfo

```typescript
interface ModelInfo {
  name: string;                // Model ID used in API calls
  label: string;               // Human-readable display name
  provider: string;            // Provider name
  maxTokenAllowed: number;     // Context window size (input tokens)
  maxCompletionTokens?: number; // Maximum output tokens
  tpm?: number;                // Tokens per minute limit
  rpm?: number;                // Requests per minute limit
}
```

## Static vs Dynamic Model Discovery

Providers can supply models in two ways:

### Static Models

Declared in the `staticModels` array. These are always available regardless of API key status and serve as **fallback models** when the provider's API is unreachable or the user hasn't configured a key yet. Static models are registered immediately when the provider is instantiated.

### Dynamic Models

Fetched at runtime via the `getDynamicModels` method, which calls the provider's `/models` or equivalent endpoint. Dynamic models are:

- **Cached** per session using a cache key derived from the API key and settings
- **Lazy-loaded** — only fetched when the model list is requested
- **Time-guarded** — a 5-second timeout prevents hanging fetches
- **Deduped** — any model already present in `staticModels` is filtered out

The `LLMManager.updateModelList` method combines both sources: it filters enabled providers, fetches dynamic models with caching, and merges them with the static list.

## Provider Enable/Disable

Each provider can be toggled on or off in **Settings → Providers**. When a provider is disabled:

- Its models are excluded from the model selector
- Its `getDynamicModels` is never called
- Its API key is not sent to the server

The enabled/disabled state is persisted per-provider in the `providerSettings` store and stored in localStorage under the `provider_settings` key.

## Custom Providers

Amplify supports **any OpenAI-compatible endpoint** as a custom provider. Users can add custom providers in two ways:

1. **Via UI** — The "Add Provider" popup in the model selector lets you specify a name, base URL, and API key. This is stored in the `customProvidersStore` (localStorage key `amplify_custom_providers`).

2. **Via code** — Extend `BaseProvider` and register it with `LLMManager`. See the [Custom Providers](/docs/providers/custom-providers) page for the step-by-step guide.

Custom providers appear in the model selector as a dedicated "Custom" group. Their models are fetched lazily from the endpoint's `/v1/models` path.

## Model Selector UI

The model selector (`ModelSelector.tsx`) provides:

- **Grouped display** — Models grouped by provider (cloud, local, custom)
- **Fuzzy search** — Levenshtein-distance-based search across model names and labels
- **Keyboard navigation** — Arrow keys, Enter to select, Escape to close
- **Context info** — Each model shows its context window size (e.g. "200k context")
- **Pricing info** — OpenRouter and Together models show per-token pricing in the label
- **API key management** — Missing keys trigger the API key popup inline

When you select a model, Amplify uses the provider's `getModelInstance` method to create an AI SDK `LanguageModel` instance, which handles streaming, tool calling, and structured output.

## Docker Considerations

When running Amplify inside Docker, local provider URLs that reference `localhost` or `127.0.0.1` must be rewritten to `host.docker.internal` so the container can reach services on the host machine. The `BaseProvider.resolveDockerUrl` method handles this automatically when the `RUNNING_IN_DOCKER=true` environment variable is set.

See [Local Providers](/docs/providers/local-providers) for details.
