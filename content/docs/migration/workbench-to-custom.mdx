# Migrate from Workbench to Custom Server

When you need to run your Amplify project outside of both the WebContainer sandbox and Docker, you can deploy directly to a custom server. This guide covers migrating to a bare metal server, VPS, or cloud VM.

## When to Choose Custom Server

A custom server deployment is appropriate when:

- You need full control over the runtime environment
- Docker overhead is undesirable (performance-sensitive scenarios)
- Your infrastructure doesn't support Docker
- You need specialized hardware access (GPU for local models)
- You're integrating Amplify into an existing server architecture

## Migration Process

### Step 1: Export the Project

Same as the Docker migration:

1. Export project files as ZIP from the workbench
2. Or push to a Git repository from the WebContainer terminal

```bash
# In the WebContainer terminal
git init
git add .
git commit -m "export for custom deployment"
git push origin main
```

### Step 2: Set Up the Target Server

Prepare your server with the required software:

```bash
# Install Node.js 18+
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt-get install -y nodejs

# Install pnpm
npm install -g pnpm

# Install git
sudo apt-get install -y git
```

### Step 3: Clone and Build Amplify

```bash
# Clone Amplify
git clone https://github.com/nicepkg/amplify.git
cd amplify

# Install dependencies
pnpm install --frozen-lockfile

# Build for production
NODE_OPTIONS=--max-old-space-size=4096 pnpm run build
```

### Step 4: Transfer Project Files

Clone the exported project onto the server:

```bash
# Clone from your repository
git clone https://github.com/your-org/your-project.git /opt/project
```

Or copy files directly:

```bash
# SCP transfer
scp -r ./exported-project/* user@server:/opt/project/
```

### Step 5: Configure and Start

```bash
# Create environment configuration
cat > .env.local << 'EOF'
OPENAI_API_KEY=sk-your-key
ANTHROPIC_API_KEY=sk-ant-your-key
PORT=5173
NODE_ENV=production
EOF

# Start with Wrangler
bindings=$(./bindings.sh) && wrangler pages dev ./build/client $bindings
```

### Step 6: Set Up Reverse Proxy

Configure a reverse proxy for SSL and security headers (see [Native Deployment](/docs/self-hosting/native) for nginx/Caddy configurations).

## Key Differences from Docker Migration

| Aspect | Docker Migration | Custom Server Migration |
|--------|-----------------|------------------------|
| Runtime isolation | Container sandbox | Full system access |
| Deployment complexity | Low (single command) | Medium (multiple steps) |
| Resource efficiency | Slight overhead | No overhead |
| Native binary support | Inside container | Direct system access |
| GPU access | Requires passthrough | Direct access |
| Updates | Pull new image | Git pull + rebuild |
| Local model hosting | host.docker.internal | localhost directly |

## Running Local Models on the Custom Server

A major advantage of custom server deployment is direct access to local LLM models:

### Ollama on the Server

```bash
# Install Ollama
curl -fsSL https://ollama.com/install.sh | sh

# Pull a model
ollama pull llama3.1

# Configure Amplify to use it
OLLAMA_API_BASE_URL=http://localhost:11434
```

Since the server is not in Docker, `localhost` works directly — no `host.docker.internal` rewriting needed.

### LM Studio on the Server

Install LM Studio on the server (requires GUI or headless mode) and configure:

```bash
LMSTUDIO_API_BASE_URL=http://localhost:1234
```

## GPU Configuration

If your server has a GPU for local model inference:

```bash
# Check GPU availability
nvidia-smi

# Install CUDA drivers if needed
sudo apt-get install -y nvidia-driver-535

# Ollama automatically uses GPU when available
ollama pull llama3.1  # Uses GPU for inference
```

## Process Management

Use systemd or PM2 for production process management (see [Native Deployment](/docs/self-hosting/native) for detailed configurations).

## Chat and Memory Migration

The same export/import process applies:

1. **Chat history** — Export as JSON, import in the new browser session
2. **Vector store** — Export via Memory tab, import in the new session
3. **Settings** — Export API keys configuration, re-enter in the new session

Since all persistent data is browser-side (IndexedDB), the server change doesn't affect data storage — you just need to re-import from the exported files.

## Security Considerations

Custom server deployments require manual security configuration:

- [ ] SSL/TLS certificate installed
- [ ] COEP/COOP headers configured (required for WebContainers)
- [ ] Firewall rules set (only expose 443 for HTTPS)
- [ ] API keys stored securely (not in publicly accessible files)
- [ ] Regular updates for Node.js, OS packages, and dependencies
- [ ] Log rotation configured
- [ ] Rate limiting on the reverse proxy

## Common Migration Issues

| Issue | Solution |
|-------|----------|
| Build fails on server | Ensure Node.js 18+ and sufficient memory (4 GB) |
| Wrangler not found | Install wrangler: `npm install -g wrangler` |
| COEP headers missing | Configure in reverse proxy |
| Local models unreachable | Check Ollama/LM Studio is running on the specified port |
| GPU not detected | Install NVIDIA drivers and verify with nvidia-smi |
