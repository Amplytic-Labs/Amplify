# API Migration

This guide covers migrating between Amplify API versions, including breaking changes, deprecated endpoints, and upgrade strategies.

## Version History

Amplify follows semantic versioning for its API routes. Major version changes may include breaking changes that require updates to client code or integrations.

## Current API Structure

Amplify's API routes are defined in `app/routes/` using Remix's file-based routing. The current API structure includes:

### Chat API

|----------|--------|-------|

| `/api/llmcall` | Current | Direct LLM call for sub-chats |
| `/api/enhancer` | Current | Prompt enhancement endpoint |
| `/api/plan` | Current | Planning system API |

## Migration Strategies

### Strategy 1: In-Place Upgrade

The simplest approach — update Amplify and verify compatibility:

```bash
# Pull the latest version
git pull origin main

# Install any new dependencies
pnpm install

# Build
pnpm run build

# Start and verify
pnpm run start
```

Check for breaking changes by:
1. Reviewing the changelog
2. Testing all API endpoints
3. Verifying MCP integrations still work
4. Checking provider connectivity

### Strategy 2: Parallel Deployment

Deploy the new version alongside the old one for gradual migration:

```bash
# Run old version on port 5173
# Run new version on port 5174

# Test new version
curl http://localhost:5174/api/health

# Switch traffic when confident
# Update reverse proxy to point to 5174
```

### Strategy 3: Canary Deployment

For production deployments with multiple users:

1. Deploy the new version to a single instance
2. Route a small percentage of traffic to the new instance
3. Monitor for errors and compatibility issues
4. Gradually increase traffic to the new version
5. Remove the old version once fully migrated

## Breaking Changes by Version

### Vercel AI SDK v7 Migration

The migration from AI SDK v3/v4 to v7 introduced significant changes:

| Change | Impact | Migration Action |
|--------|--------|-----------------|
| New streaming format | Client-side streaming handler must use v7 API | Update `useChat` and streaming hooks |
| Tool call format | Tool invocations use new annotation format | Update tool rendering components |
| Provider API | Provider creation uses new factory pattern | Update all provider `getModelInstance` methods |
| Message format | Messages use new `UIMessage` type | Update message parsing and storage |

The v7 SDK is already integrated in the current Amplify version. If you're upgrading from an older version, ensure all client-side hooks and components use the v7 API.

### Remix v2 Migration

Amplify uses Remix v2 with the Vite plugin:

| Change | Impact | Migration Action |
|--------|--------|-----------------|
| Vite-based build | Replaces Remix esbuild compiler | Update build scripts and config |
| New route format | Routes use `.tsx` extension | Rename route files |
| Future flags | Several v2 future flags required | Add to `remix.config` |

### Provider SDK Updates

Provider SDKs are updated independently. Key changes to watch:

| SDK | Change | Impact |
|-----|--------|--------|
| `@ai-sdk/openai` v4 | New model IDs, streaming format | Update model definitions |
| `@ai-sdk/anthropic` v4 | New Claude models, thinking support | Update model definitions |
| `@ai-sdk/google` v4 | Gemini 2.x models | Update model definitions |
| `@ai-sdk/amazon-bedrock` v5 | New region support | Update config format |

When upgrading provider SDKs:
1. Check the SDK's changelog for new model IDs
2. Update `staticModels` arrays in provider files
3. Test dynamic model discovery with the new SDK
4. Verify streaming format compatibility

## MCP Configuration Migration

MCP server configurations may need updates when:

- The MCP SDK version changes (`@modelcontextprotocol/sdk`)
- Transport protocols are updated (new SSE/HTTP specs)
- Tool schema formats change

Current MCP SDK version: v1.29+

```bash
# Check MCP SDK version
pnpm list @modelcontextprotocol/sdk
```

### Transport Migration

| Transport | Current Spec | Migration Notes |
|-----------|-------------|-----------------|
| stdio | Stable | No changes needed |
| SSE | Stable | No changes needed |
| Streamable HTTP | New (v2025) | May require server updates |

If you're using SSE-based MCP servers, consider migrating to Streamable HTTP for better performance and simpler deployment.

## Data Migration

### IndexedDB Schema Changes

When the IndexedDB schema changes (new stores, modified fields):

1. Export all data via the Memory tab
2. Update Amplify
3. Import data — the new schema will handle migration automatically
4. Verify all entries are intact

### localStorage Changes

When localStorage key names or formats change:

1. The `readFromStorage()` function merges user values with defaults
2. New keys get their suggested defaults
3. Old keys with undefined values are stripped
4. No manual intervention needed for most changes

## Testing After Migration

After upgrading, verify these critical paths:

1. **Chat streaming** — Send a message and verify SSE streaming works
2. **Tool invocations** — Verify native and MCP tools execute correctly
3. **Model selection** — Check that all providers and models appear
4. **WebContainer** — Boot a project and verify the preview works
5. **Persistence** — Verify chat history and settings persist across refreshes
6. **Vector store** — Search for context entries and verify relevance
7. **Rate limits** — Test with a high-volume request and verify throttling
8. **Deployment** — Deploy to Vercel/Netlify and verify the deployment link

## Rollback Plan

If a migration causes issues:

1. Keep the previous version's build output available
2. Document the exact version you're rolling back to
3. Revert the reverse proxy to the old version
4. Restore IndexedDB data from the exported backup
5. Investigate the issue before re-attempting the migration

```bash
# Quick rollback
git checkout v1.0.0  # Previous stable version
pnpm install
pnpm run build
pnpm run start
```
