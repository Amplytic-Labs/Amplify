# Native Deployment

For environments where Docker or Cloudflare Pages aren't suitable, Amplify can be deployed directly on a server using Node.js. This approach gives you full control over the runtime environment.

## Prerequisites

- Node.js 18.18.0 or later
- pnpm (recommended)
- A server with sufficient memory (4 GB+ recommended)
- A reverse proxy (nginx, Caddy, etc.) for production

## Build for Production

```bash
# Clone and install
git clone https://github.com/nicepkg/amplify.git
cd amplify
pnpm install --frozen-lockfile

# Build the Remix app
NODE_OPTIONS=--max-old-space-size=4096 pnpm run build
```

The build creates:
- `build/client/` — Client-side assets (HTML, JS, CSS, fonts)
- `build/server/` — Server-side Remix bundle

## Start the Production Server

### Using Wrangler (Recommended)

Amplify uses Wrangler as the production server runtime (same as Cloudflare Pages):

```bash
# Unix (with bindings)
bindings=$(./bindings.sh) && wrangler pages dev ./build/client $bindings

# Windows
wrangler pages dev ./build/client
```

### Using a Custom Server

If you prefer not to use Wrangler, you can serve the build output with any static file server and add a Remix server adapter:

```bash
# Simple static server for client assets
npx serve ./build/client -l 5173
```

Note: This approach only serves static files. For full SSR functionality, you need a Remix-compatible server adapter.

## Environment Configuration

Create `.env.local` with your configuration:

```bash
# Server settings
PORT=5173
NODE_ENV=production

# Provider API keys
OPENAI_API_KEY=sk-your-key
ANTHROPIC_API_KEY=sk-ant-your-key
GOOGLE_GENERATIVE_AI_API_KEY=your-key

# Optional settings
DEFAULT_NUM_CTX=32768
VITE_LOG_LEVEL=info
```

## Process Management

For production deployments, use a process manager to ensure Amplify stays running:

### systemd

Create a systemd service file:

```ini
[Unit]
Description=Amplify AI Coding Environment
After=network.target

[Service]
Type=simple
User=amplify
WorkingDirectory=/opt/amplify
ExecStart=/usr/bin/node -e "require('./bindings.sh')()" && wrangler pages dev ./build/client
Restart=always
RestartSec=5
Environment=NODE_ENV=production
Environment=PORT=5173

[Install]
WantedBy=multi-user.target
```

```bash
# Enable and start
sudo systemctl enable amplify
sudo systemctl start amplify
```

### PM2

```bash
# Install PM2
npm install -g pm2

# Start Amplify
pm2 start "pnpm run start:unix" --name amplify

# Save process list
pm2 save

# Set up auto-restart on reboot
pm2 startup
```

### Docker Compose (Simple)

Even without the full Docker build, you can use Docker Compose for process management:

```yaml
services:
  amplify:
    image: node:22-bookworm-slim
    working_dir: /app
    volumes:
      - ./build:/app/build
      - ./node_modules:/app/node_modules
      - ./package.json:/app/package.json
      - ./bindings.sh:/app/bindings.sh
    ports:
      - "5173:5173"
    env_file: .env.local
    command: pnpm run start:unix
```

## Reverse Proxy Setup

A reverse proxy is essential for production deployments to handle SSL, security headers, and load balancing.

### Nginx

```nginx
server {
    listen 443 ssl http2;
    server_name amplify.example.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    # Required for WebContainers
    add_header Cross-Origin-Embedder-Policy "credentialless" always;
    add_header Cross-Origin-Opener-Policy "same-origin" always;

    location / {
        proxy_pass http://127.0.0.1:5173;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # SSE support
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 86400s;
        proxy_send_timeout 86400s;
    }
}
```

Key configuration for SSE streaming:
- `proxy_buffering off` — Don't buffer streaming responses
- `proxy_read_timeout 86400s` — Allow long-lived SSE connections
- COEP/COOP headers — Required for WebContainers

### Caddy

```
amplify.example.com {
    reverse_proxy localhost:5173

    header Cross-Origin-Embedder-Policy "credentialless"
    header Cross-Origin-Opener-Policy "same-origin"
}
```

Caddy handles SSL automatically with Let's Encrypt and provides simpler configuration than nginx.

## SSL/TLS Configuration

SSL is required for WebContainers because:
- `SharedArrayBuffer` (needed for WebAssembly) requires a secure context
- COEP/COOP headers only work with HTTPS
- Most modern browser APIs require HTTPS

Options for SSL:
- **Let's Encrypt** — Free certificates via Certbot or Caddy
- **Cloudflare SSL** — If using Cloudflare as a proxy
- **Commercial certificates** — From certificate authorities

## Memory and Performance

| Setting | Recommendation |
|---------|---------------|
| Node.js memory | 4 GB+ (`--max-old-space-size=4096`) |
| Server RAM | 8 GB+ (accounts for multiple users) |
| CPU | 2+ cores |
| Storage | 10 GB+ for build output and dependencies |

The Remix build process requires significant memory. Use `NODE_OPTIONS=--max-old-space-size=4096` during the build step.

## Scaling Considerations

Amplify is primarily a single-user application (each browser session is independent). However, for multi-user deployments:

- **Horizontal scaling** — Deploy multiple instances behind a load balancer
- **Session affinity** — Not required (all state is in the browser)
- **Shared state** — Only server-side API keys need to be consistent across instances

Since all persistent data (chat history, settings, vector store) lives in the browser's IndexedDB, the server instances only need to serve the application and proxy LLM API calls.

## Monitoring

```bash
# Health check
curl http://localhost:5173/api/health

# System diagnostics
curl http://localhost:5173/api/system/diagnostics

# Check configured providers
curl http://localhost:5173/api/configured-providers
```

Set up monitoring tools (Prometheus, Grafana, etc.) to track:
- Application uptime
- Response latency
- Error rates
- Memory usage

## Security Checklist

- [ ] HTTPS enabled with valid certificate
- [ ] COEP/COOP headers configured
- [ ] API keys stored securely (not in plaintext files accessible to the web)
- [ ] Firewall configured to only expose port 443 (HTTPS)
- [ ] Regular security updates for Node.js and dependencies
- [ ] Rate limiting on the reverse proxy
- [ ] CORS configured correctly
