# Orama Vector Database

Amplify uses **Orama v3** as its vector database engine for persistent context management. Orama provides full-text search with **BM25 ranking** (the industry-standard relevance algorithm), persisted to **IndexedDB** for browser-side storage.

## Why Orama

Orama was chosen for several reasons:

- **BM25 ranking** — The gold standard for full-text search relevance
- **IndexedDB persistence** — Data persists across browser sessions without server infrastructure
- **Type-safe schemas** — Strongly typed search indices prevent runtime errors
- **Zero dependencies** — No external database server required
- **Small footprint** — Minimal memory and storage overhead
- **Fast inserts** — Efficient batch insertion for context entries

Unlike traditional vector databases that use embedding-based similarity (requiring an embedding model), Orama uses BM25 keyword matching. This works well for Amplify's use case because:
- Context entries are structured text (requirements, decisions, patterns)
- Keyword relevance is more predictable than embedding similarity
- No additional embedding model is needed
- Search results are deterministic and reproducible

## Two Store Architecture

Amplify maintains two separate Orama stores:

### User Profile Store

Stores long-term user preferences and patterns that apply across all projects.

**Schema Properties (searchable):**
- `id` — Unique identifier
- `content` — The preference/knowledge text (primary search target)
- `category` — Entry category (preference, tech_stack, coding_style, etc.)
- `createdAt` — Creation timestamp
- `updatedAt` — Last update timestamp
- `accessCount` — How many times retrieved
- `source` — Origin of the entry
- `confidence` — Confidence score

**Search Modes:**
- Full-text search on `content` with BM25 ranking
- Filter by `category` for targeted retrieval
- Filter by `confidence` threshold for quality control

### Project Context Store

Stores project-specific knowledge that persists across sessions within a project.

**Schema Properties (searchable):**
- `id` — Unique identifier
- `projectId` — Project association
- `content` — The context text (primary search target)
- `type` — Entry type (requirement, decision, error, fix, etc.)
- `createdAt` — Creation timestamp
- `updatedAt` — Last update timestamp
- `sourceChatId` — Originating chat session
- `planPointId` — Originating plan point
- `files` — Related file paths
- `tags` — Categorization tags

**Search Modes:**
- Full-text search on `content` with BM25 ranking
- Filter by `projectId` for project-scoped retrieval
- Filter by `type` for specific entry categories
- Filter by `tags` for tag-based retrieval

## Search Configuration

Both stores support flexible search options:

| Option | Default | Description |
|--------|---------|-------------|
| `limit` | 10 | Maximum number of results to return |
| `threshold` | 0.5 | Minimum relevance score (0.0 to 1.0) |
| `category` | — | Filter to a specific category/type |
| `tags` | — | Filter to entries with specific tags |
| `properties` | `["content"]` | Which properties to search in |

### Relevance Threshold

The `threshold` option controls quality filtering:
- `0.0` — Return all results regardless of relevance
- `0.5` — Return only moderately relevant results (default)
- `0.8` — Return only highly relevant results
- `1.0` — Return only perfectly matching results

Setting a higher threshold reduces noise but may miss relevant entries that use different terminology.

## Context Injection

When a new chat session starts, the vector stores are queried for relevant context:

### Injection Process

1. The system prompt builder receives the user's message
2. It searches the User Profile Store for matching preferences
3. It searches the Project Context Store for matching project knowledge
4. Top-k results from each store are formatted as labeled sections
5. The formatted context is injected into the system prompt
6. The AI receives both the current task and relevant past context

### Token Budget

Context injection respects a token budget to avoid overloading the system prompt:
- User profile entries: limited to top 5 results
- Project context entries: limited to top 10 results
- Total context injection: capped at ~2000 tokens
- If the budget is exceeded, lower-relevance entries are dropped

## Persistence Layer

The `persistence.ts` module handles database lifecycle:

### Database Creation

```typescript
// Create a new Orama database with schema
const db = await create({
  schema: {
    id: 'string',
    content: 'string',
    category: 'string',
    createdAt: 'string',
    updatedAt: 'string',
    accessCount: 'number',
    source: 'string',
    confidence: 'number',
  },
});
```

### Data Operations

| Operation | Description |
|-----------|-------------|
| `insert` | Add a single entry |
| `insertMultiple` | Batch insert multiple entries |
| `search` | BM25 full-text search |
| `update` | Modify an existing entry |
| `remove` | Delete an entry |

### Storage Location

Orama databases are stored in IndexedDB:
- Each store gets its own IndexedDB database
- Data persists across browser sessions
- Storage is scoped to the browser origin
- Data can be exported/imported for backup

## Vector Store Hooks

Amplify provides React hooks for accessing vector stores:

### useVectorContext

The `useVectorContext` hook provides search functionality in React components:

```typescript
const { search, results, isLoading } = useVectorContext();

// Search for relevant context
const entries = await search({
  term: "authentication patterns",
  limit: 5,
  threshold: 0.7,
});
```

### useProjectContext

The `useProjectContext` hook loads project-specific context:

```typescript
const { context, addEntry, removeEntry } = useProjectContext(projectId);

// Add a new context entry
addEntry({
  content: "Using JWT for authentication",
  type: "decision",
  tags: ["auth", "security"],
});
```

## Integration with Planning

The vector stores are deeply integrated with the planning system:

1. **Plan creation** — User profile and project context inform the planner
2. **Sub-chat context** — Each worker receives vector-store-retrieved context instead of full history
3. **Result storage** — Sub-chat outcomes are stored as new context entries
4. **Verification context** — Past error patterns help identify common issues

This creates a feedback loop where every interaction enriches the knowledge base.

## Performance Considerations

- **Search latency** — BM25 search is fast (typically under 50ms for small datasets)
- **Index size** — Grows linearly with the number of entries
- **Insert cost** — Batch inserts are more efficient than single inserts
- **Memory usage** — Orama keeps the index in memory during search operations
- **Storage cleanup** — Low-confidence and stale entries can be pruned periodically
