# LLM Pipeline

The LLM pipeline is the core engine that connects Amplify's chat interface to 22+ language model providers. It uses the **Vercel AI SDK v7** with a custom provider registry pattern for dynamic model discovery and routing.

## Provider Registry Pattern

Amplify uses a singleton `LLMManager` that registers all providers at startup. Each provider extends the `BaseProvider` abstract class, which defines the interface for model listing, model instantiation, and configuration.

### BaseProvider Interface

Every provider implements these core properties and methods:

| Member | Type | Description |
|--------|------|-------------|
| `name` | string | Provider identifier (e.g., "OpenAI", "Anthropic") |
| `staticModels` | ModelInfo array | Hardcoded list of well-known models |
| `config` | ProviderConfig | API key name, base URL key, and defaults |
| `getDynamicModels()` | async method | Fetches available models from the provider's API at runtime |
| `getModelInstance()` | method | Creates a Vercel AI SDK LanguageModel for a given model ID |
| `getApiKeyLink` | string | URL where users can obtain an API key |
| `labelForGetApiKey` | string | Human-readable label for the API key link |
| `icon` | string | Icon identifier for the UI |

### ModelInfo Structure

Each model entry contains:

| Field | Type | Description |
|--------|------|-------------|
| `name` | string | Model ID used in API calls (e.g., "gpt-4o") |
| `label` | string | Human-readable name (e.g., "GPT-4o") |
| `provider` | string | Provider name (e.g., "OpenAI") |
| `maxTokenAllowed` | number | Maximum context window (input tokens) |
| `maxCompletionTokens` | number | Maximum output tokens (optional, falls back to provider defaults) |
| `tpm` | number | Tokens per minute limit (optional) |
| `rpm` | number | Requests per minute limit (optional) |

### LLMManager Lifecycle

The `LLMManager` singleton manages the full lifecycle:

1. **Registration** — All provider classes from the registry are instantiated and registered at startup
2. **Model List** — Static models are collected; dynamic models are fetched on demand
3. **Model Selection** — The chat route selects a provider and model based on user configuration
4. **Streaming** — The Vercel AI SDK handles streaming responses with tool call support
5. **Rate Limiting** — Pre-flight checks enforce user-configured RPM/TPM/RPD limits

### Dynamic Model Discovery

Providers like OpenAI, Anthropic, Ollama, LM Studio, OpenRouter, Together, and HuggingFace support dynamic model discovery. When the user opens the model selector, Amplify fetches available models from the provider's API endpoint using the configured API key.

```typescript
// Dynamic model fetch (simplified)
async getDynamicModels(apiKeys, settings, serverEnv) {
  const response = await fetch(this.getProviderBaseUrl() + '/models', {
    headers: { Authorization: 'Bearer ' + apiKey },
    signal: AbortSignal.timeout(5000), // 5-second timeout
  });
  return response.data.map(m => ({
    name: m.id,
    label: m.id,
    provider: this.name,
    maxTokenAllowed: m.context_length || defaultContext,
  }));
}
```

### Provider Caching

Dynamic model lists are cached with a `cacheId` based on the API key. When the same key is used, cached models are returned immediately without re-fetching. The cache is invalidated when the API key changes.

## Chat Pipeline Flow

When a user sends a message, the following pipeline executes:

### Step 1: Context Collection

The client collects and sends:
- Current file map (all files in the WebContainer)
- Chat history (previous messages in the conversation)
- Selected provider and model configuration
- Rate limit settings for the current provider
- MCP tool definitions from connected servers
- Active skill contexts

### Step 2: System Prompt Construction

The server builds a comprehensive system prompt including:
- Project context from the vector store (relevant patterns, decisions, constraints)
- Skill-specific guidance (if skills are enabled for this project)
- File structure summary (from the file map)
- Tool definitions (native tools + MCP tools)
- Rate limit warnings (if applicable)

### Step 3: Provider Resolution

The `LLMManager` resolves the model instance:
1. Look up the provider by name in the registry
2. Find the model in the provider's model list
3. Create a Vercel AI SDK `LanguageModel` instance with the API key and base URL
4. For local providers, rewrite `localhost` URLs to `host.docker.internal` if running in Docker

### Step 4: Rate Limit Pre-Flight

Before sending the request to the LLM:
1. Estimate the token count from the combined message sizes
2. Check if the request would exceed the user's TPM cap
3. If auto-shrink is enabled, reduce context (summarize earlier messages) to fit
4. Enforce RPM throttling (sleep if too many requests in the last 60 seconds)

### Step 5: Streaming Response

The Vercel AI SDK streams the response back to the client via SSE:
- Text content streams token-by-token for immediate display
- Tool call annotations stream as structured JSON parts
- Reasoning/thinking content streams in dedicated parts (for models that support it)

### Step 6: Tool Execution

When the LLM invokes a tool:
1. **Native tools** (read_file, list_dir, etc.) execute on the server using the file map from the request
2. **MCP tools** route to the connected MCP server via stdio/SSE/HTTP transport
3. **Mutating tools** (create_file, replace_string) return mutation signals instead of directly modifying files
4. Tool results are fed back to the LLM for the next response turn

### Step 7: Client-Side Mutation

The browser-side chat handler processes tool results:
1. Detects mutation signals in tool results
2. Applies mutations to the workbench file store (Zustand)
3. The file store writes changes to the WebContainer
4. The preview refreshes automatically

## Rate Limiting Architecture

Rate limiting is a critical part of the pipeline. The system uses a three-tier approach:

### Pre-Flight Check

Before the LLM request is sent, the server estimates token usage and rejects requests that would exceed the user's TPM cap. This prevents wasted API calls that would result in 429 errors.

### RPM Throttling

Requests per minute are enforced by tracking recent request timestamps. If the RPM limit is reached, the server delays the request until the window resets.

### Auto-Shrink

When the estimated token count exceeds the TPM limit, the server automatically:
1. Summarizes older messages to reduce context size
2. Removes redundant file content from the system prompt
3. Keeps only the most recent and relevant context

This is controlled by the `autoShrinkToTpm` setting per provider.

## Provider-Specific Details

Each provider has unique characteristics that the pipeline handles:

### Cloud Providers with Static Models

Providers like Anthropic, OpenAI, and Cerebras ship hardcoded model lists as `staticModels`. These are always available regardless of API connectivity.

### Cloud Providers with Dynamic Models

Providers like OpenRouter, Together, and HuggingFace fetch their full model catalogs dynamically. Static models serve as fallbacks when the API is unreachable.

### Local Providers

Ollama, LM Studio, and OpenAI-like providers have **no static models** — all models are discovered dynamically from the local server. These providers:
- Use configurable base URLs (not fixed provider endpoints)
- Support Docker URL rewriting (`localhost` → `host.docker.internal`)
- Have no rate limits (all set to 0/unlimited)

### Amazon Bedrock

Amazon Bedrock uses a special JSON configuration (`AWS_BEDROCK_CONFIG`) containing region, access key, secret key, and optional session token. The provider parses this JSON to create the AWS SDK client.

### Z.ai

Z.ai includes a custom fetch wrapper that transparently retries transient upstream errors (502, 503, 504) with exponential backoff and fallback base URLs.
