# Architecture Overview

Amplify is a full-stack AI coding environment built on a client-server architecture where the server handles LLM orchestration and the client manages the interactive workspace. This separation allows the file system and execution environment to live entirely in the browser via WebContainers.

## High-Level Architecture

Amplify consists of several interconnected subsystems:

1. **Frontend (Remix v2 + Vite)** — The UI layer with SSR support, deployed to Cloudflare Pages
2. **LLM Pipeline (Vercel AI SDK v7)** — Provider registry, model discovery, and streaming chat
3. **WebContainer Runtime** — Browser-side Node.js execution via StackBlitz WebContainers
4. **State Management (Zustand + Nanostores)** — Reactive client-side stores with IndexedDB persistence
5. **Planning System** — Task decomposition with sub-chats, verification, and checkpoints
6. **MCP Integration** — External tool and data source connectivity via Model Context Protocol
7. **Vector Store (Orama)** — Full-text search for project context and user profile memory
8. **Native Tools** — Copilot-style file operations operating on browser-side file maps

## Client-Server Communication

The communication flow follows this pattern:

```
Browser (Client)                          Server (Cloudflare Workers)
┌─────────────────────┐                  ┌─────────────────────────┐
│  Chat UI             │  POST /api/chat  │  LLM Manager            │
│  Workbench           │  ──────────────► │  Provider Registry      │
│  WebContainer        │                  │  MCP Service            │
│  File Store          │  Streaming SSE   │  Native Tool Execution  │
│  Vector Store        │  ◄────────────── │  Rate Limit Enforcer    │
│  IndexedDB           │                  │  Prompt Builder         │
└─────────────────────┘                  └─────────────────────────┘
```

### Key Design Principle: Mutation Signals

Mutating tools (file create, file edit, string replace) do **not** directly touch the file system on the server. Instead, they return structured **mutation signals** (JSON). The browser-side chat handler detects these signals in tool results and applies them to the workbench file store, which then writes to the WebContainer.

This design ensures:
- The server never needs filesystem access
- The authoritative file state lives in the browser (consistent with WebContainer)
- The AI sees the same file snapshot used by the system prompt context builder

## Data Flow

### Chat Flow

1. User sends a message from the Chat UI
2. Client collects current file map, chat history, and settings
3. POST request to `/api/chat` with all context
4. Server builds system prompt from project context, skills, and MCP tools
5. LLM Manager selects the configured provider and model
6. Streaming response begins (SSE) with tool call annotations
7. Native tools and MCP tools execute on the server side
8. Mutation signals are sent back to the client
9. Client applies mutations to the workbench file store
10. WebContainer reflects file changes in the preview

### Planning Flow

1. User sends a complex task
2. AI generates a Plan with N PlanPoints
3. Each PlanPoint is executed as an independent sub-chat
4. Sub-chats access project context via vector store (no full context dump)
5. After each sub-chat, results are extracted and stored in vector DB
6. Verification runs (lint, type-check, flow verification)
7. AI returns to main chat with summary of what was done
