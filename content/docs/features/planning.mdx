# Planning System

The planning system is Amplify's approach to handling complex, multi-step tasks. Instead of trying to accomplish everything in a single long conversation (which consumes tokens rapidly and often loses coherence), the planning system decomposes tasks into independent **sub-chats** with structured context sharing via the vector store.

## Why Planning Exists

Long conversations with LLMs face two fundamental problems:

1. **Token consumption** — Each turn adds the full conversation to the context, quickly exhausting the model's context window
2. **Coherence drift** — As conversations grow, the AI loses focus on earlier instructions and context

The planning system addresses both by:

- Breaking tasks into small, focused sub-chats (each with its own context window)
- Sharing context between sub-chats via the vector store (not by dumping the full conversation)
- Running verification after each step to ensure quality
- Enabling deterministic resume after interruptions

## Plan Lifecycle

A plan goes through these stages:

| Status | Description |
|--------|-------------|
| `draft` | AI is still generating the plan structure |
| `approved` | User approved (or auto-approved), execution can begin |
| `executing` | Currently executing plan points |
| `paused` | Execution paused for user intervention or error |
| `completed` | All points completed successfully |
| `failed` | One or more points failed |
| `cancelled` | User cancelled the plan |

### Step 1: Plan Creation

When the user sends a complex task:

1. The AI analyzes the task and creates a `Plan` with N `PlanPoints`
2. Each point has a title, description, goal, and expected files
3. Points may have dependencies on other points (sequential ordering)
4. Each point specifies which skills and tool outputs it needs
5. The plan is presented to the user for approval (or auto-approved)

### Step 2: Plan Execution

For each PlanPoint, the execution manager:

1. **Preparation phase** — Fetches required tool outputs and invokes specified skills
2. **Worker launch** — Starts an independent sub-chat with focused context
3. **Execution** — The worker completes the task using native and MCP tools
4. **Verification** — Runs lint, type-check, and flow verification on the changes
5. **Context extraction** — Results are extracted and stored in the vector DB

### Step 3: Completion

After all points complete:

1. The execution manager aggregates results from all sub-chats
2. A summary is generated and returned to the main chat
3. The plan status transitions to `completed`
4. Vector store entries are available for future conversations

## PlanPoint Structure

Each PlanPoint contains both an immutable **task contract** (set by the planner AI) and mutable **execution state** (managed by the runtime):

### Task Contract (Immutable)

| Field | Description |
|-------|-------------|
| `title` | Short, human-readable title |
| `goal` | One or two sentences describing what "done" looks like |
| `description` | Detailed implementation notes for the worker |
| `requirements` | Explicit requirements the implementation must satisfy |
| `successCriteria` | Criteria for verification to decide if the task is truly complete |
| `requiredSkills` | Skills to invoke before the worker starts |
| `requiredToolOutputs` | References to tool outputs to fetch and inject |
| `expectedFiles` | Files this task is expected to create or modify |
| `verificationChecks` | Types of verification to run after completion |
| `constraints` | Explicit boundaries (files not to modify, packages not to install) |

### Execution State (Mutable)

| Field | Description |
|-------|-------------|
| `status` | Current execution status (pending, running, verifying, completed, etc.) |
| `startedAt` | When execution began |
| `completedSteps` | Human-readable list of steps completed |
| `filesModified` | List of files changed so far |
| `retryCount` | Number of retry attempts after failure |
| `canResume` | Whether the task can be resumed after interruption |

## Sub-Chat Architecture

Each PlanPoint is executed as an independent sub-chat:

```
Main Chat (Task: "Build a full-stack app")
  │
  ├── Sub-Chat 1: "Set up project structure"
  │     ├── User message: task contract description
  │     ├── Tool calls: create_file, list_dir
  │     └── Result: project files created
  │
  ├── Sub-Chat 2: "Implement authentication"
  │     ├── Context from vector store: patterns, decisions
  │     ├── Tool calls: create_file, replace_string
  │     └── Result: auth module implemented
  │
  ├── Sub-Chat 3: "Build dashboard UI"
  │     ├── Context from vector store: architecture notes
  │     ├── Tool calls: create_file, read_file
  │     └── Result: dashboard components created
  │
  └── Summary returned to main chat
```

### Context Sharing

Sub-chats do NOT receive the full main chat conversation. Instead:

1. The **vector store** provides relevant context entries (requirements, decisions, patterns, architecture)
2. **Skill contexts** are injected for the required skills
3. **Tool output references** are resolved and injected at runtime
4. Only the task contract becomes the worker's primary instruction

This keeps each sub-chat's context lean and focused, dramatically reducing token usage.

## Verification System

After each PlanPoint completes, the verification system checks the results:

### Verification Types

| Type | Description |
|------|-------------|
| `lint` | ESLint / style checking on modified files |
| `type_check` | TypeScript type checking on the project |
| `flow_verification` | "Every button does something" and "every screen is connected" |
| `build_check` | Does the project build successfully? |

### Verification Results

Each verification produces a `VerificationResult`:
- `passed` — Boolean indicating success
- `message` — Human-readable result description
- `issues` — List of specific problems found (with file path, line, severity, and suggestions)

If verification fails, the PlanPoint can be:
- **Retried** — The worker attempts the task again with verification feedback
- **Skipped** — Mark as skipped if the failure is in a non-critical area
- **Failed** — Mark as failed and report the issue to the main chat

## Checkpoint System

Checkpoints provide deterministic resume after interruptions:

### When Checkpoints Are Taken

- Every N tool calls (configurable, default 3)
- Before verification begins
- On explicit request

### Checkpoint Contents

| Field | Description |
|-------|-------------|
| `index` | Sequential checkpoint number |
| `filesChanged` | Files modified since the previous checkpoint |
| `toolsUsed` | Tool calls made since the previous checkpoint |
| `progressSummary` | Structured summary (steps completed, files modified, tools called) |
| `remainingWork` | What still needs to be done (derived from task contract) |
| `messageIndex` | Sub-chat message index for resume point |

### Resume Process

If a sub-chat is interrupted (browser refresh, network error):

1. The runtime reads the latest checkpoint
2. The worker's context is reconstructed from: checkpoint data + current file state
3. Execution continues from the checkpoint's message index
4. No AI reasoning is needed to "figure out" where it was — the checkpoint provides deterministic state

## Skill Context Injection

Skills are invoked BEFORE the worker starts, and only the skills the planner marked as required are loaded:

Each skill returns a `SkillContext` with:
- `architectureNotes` — Architectural recommendations
- `implementationRules` — Hard rules the worker should follow
- `commonPitfalls` — Pitfalls to avoid
- `recommendedApis` — Recommended patterns and libraries
- `codeStandards` — Formatting and naming conventions
- `suggestedTools` — Tools the worker should invoke next

This ensures each worker has domain-specific guidance without loading irrelevant skills.

## Plan Approval

Before execution begins, the plan is presented to the user via the `PlanApprovalDialog`:

1. The dialog shows all PlanPoints with titles and descriptions
2. The user can approve, modify, or reject the plan
3. Auto-approval is available for trusted tasks
4. After approval, the execution manager begins processing points in order

## Plan Persistence

Plans are persisted in IndexedDB via the `PlanStore`:

- `plans` — All plan objects
- `chatToPlan` — Maps chat IDs to plan IDs for quick lookup
- `projectPlans` — Maps project IDs to plan IDs for project history

This enables resuming plans across browser sessions and reviewing past plan executions.
