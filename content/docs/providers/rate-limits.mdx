# Rate Limits

LLM providers enforce rate limits that can cause 429 errors and account-level cooldowns. Amplify provides per-provider rate limit configuration with three enforcement mechanisms: pre-flight checks, RPM throttling, and auto-shrink.

## Why Rate Limits Matter

The model's "context window" (1M tokens for Gemini, 200K for Claude) is almost **always larger** than the provider's TPM cap. A Gemini model that accepts 1M tokens but whose provider tier only allows 250K TPM will reject any request exceeding 250K tokens with a 429 error.

On some providers (especially DeepSeek), repeated 429 errors trigger an **account-level cooldown** that persists for hours even after the per-minute window resets. This makes rate limit management critical for uninterrupted usage.

## Rate Limit Dimensions

Each provider supports three independent limits:

| Dimension | Description | Unit |
|-----------|-------------|------|
| **RPM** | Requests Per Minute | requests/min |
| **TPM** | Tokens Per Minute (input + output combined) | tokens/min |
| **RPD** | Requests Per Day (cumulative) | requests/day |

Setting any dimension to `0` means **unlimited** (no throttling for that dimension).

## Three Enforcement Mechanisms

### 1. Pre-Flight Check

Before sending the LLM request, the server estimates the token count from message sizes and refuses to send if it would exceed the TPM cap:

- Estimated tokens = sum of all message lengths × token ratio
- If estimated tokens exceed TPM → refuse with a helpful message
- Prevents wasted API calls that would result in 429s

### 2. RPM Throttling

Requests per minute are enforced by tracking recent request timestamps:

- Each request timestamp is recorded
- Before a new request, check if RPM limit has been reached
- If reached → sleep until the oldest timestamp falls outside the 60-second window
- Prevents burst-induced 429 errors

### 3. Auto-Shrink to TPM

When the estimated token count exceeds the TPM limit and `autoShrinkToTpm` is enabled:

1. The server automatically reduces context size
2. Earlier messages are summarized to shorter versions
3. Redundant file content is removed from the system prompt
4. Only the most recent and relevant context remains
5. The request is sent with the reduced context

This is the preferred behavior for most providers because it:
- Avoids 429 errors entirely
- Preserves the most important context
- Reduces token costs

When `autoShrinkToTpm` is disabled, the server simply rejects the request with an error message.

## Configuring Rate Limits

### Via Settings Panel

1. Open Settings → Providers → select a provider
2. Adjust RPM, TPM, and RPD values
3. Toggle `autoShrinkToTpm` on/off
4. Changes are saved to localStorage immediately

### Via Store API

```typescript
import { updateRateLimit, resetRateLimit } from '~/lib/stores/rate-limit';

// Update a provider's RPM
updateRateLimit('OpenAI', { rpm: 100 });

// Reset to suggested defaults
resetRateLimit('OpenAI');
```

### Persistence

Rate limit configurations are stored in localStorage under the key `amplify:rate-limits`. They are:
- Merged with suggested defaults on load (new providers get their defaults)
- Survive browser restarts
- Override defaults for existing providers
- Can be exported/imported with other settings

## Wire Format

Only the **current provider's** rate limit config is sent to the server with each chat request (the server doesn't need every provider's settings). This is done via the `getRateLimitWire()` function:

```typescript
const rateLimits = getRateLimitWire('OpenAI');
// Returns: { rpm: 500, tpm: 200000, rpd: 0, autoShrinkToTpm: true }
```

## Provider-Specific Considerations

### DeepSeek

DeepSeek is the most sensitive to rate limit violations:
- Concurrency-limited (roughly 1 request per second)
- Repeated 429s trigger hours-long account cooldowns
- Use very conservative RPM (60 or lower)
- Always enable auto-shrink

### Google (Gemini)

Gemini's free tier is extremely limited:
- 2 RPM, 50 RPD on the free tier
- Even paid tiers start at only 100 RPM
- The 1M context window far exceeds the TPM cap
- Auto-shrink is essential for Gemini

### Groq

Groq's free tier has strict limits:
- 30 RPM, 14,400 RPD, 30K TPM
- These limits are per-account, not per-model
- Fast inference makes it tempting to send many requests

### OpenRouter

OpenRouter's free models have the tightest limits:
- 20 RPM, 1,000 RPD for free-tier models
- Paid models have provider-specific limits
- Limits vary by the underlying provider

## Common Issues

| Issue | Solution |
|-------|----------|
| Frequent 429 errors | Reduce RPM and enable auto-shrink |
| Context too large for TPM | Enable auto-shrink or reduce conversation length |
| Account cooldown on DeepSeek | Use very conservative limits (under 60 RPM) |
| Gemini free tier blocked | Upgrade to paid tier or reduce request frequency |
| Rate limits not updating | Refresh the browser; settings are persisted in localStorage |
